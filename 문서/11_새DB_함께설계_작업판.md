# 새 Supabase DB 함께 설계 — 작업판

기준일: 2026-09-25. 사용자가 DB를 자동으로 만들기보다 구조와 의도를 이해하며 직접 선택하고 싶다고 요청했다. 이 문서는 **읽기 전용 확인과 설계 질문**을 위한 작업판이다. 확정된 새 스키마나 원격 적용 결과가 아니다.

## 지금 확인한 사실

- 대상은 사용자가 지정한 `wdzzianhfnupmfbjqqac`다. VS Code 재시작 뒤 이 대화의 읽기 전용 Supabase MCP가 프로젝트 URL을 조회했고 `public` 테이블 목록은 비어 있었다. 앞선 카탈로그 조회에서 Auth 사용자와 Storage 버킷도 각각 0개였다.
- 과거 데이터는 복구하지 않아도 된다는 사용자 선택이 있다. 새 DB에 **어떤 기능까지** 되살릴지는 아직 사용자가 선택하지 않았다.
- [현재 PLAN](../PLAN.md)은 브라우저 데모를 포트폴리오 검증의 중심, 기존 Supabase 앱을 보조 자료로 둔다. 데모 자체는 브라우저 저장소를 쓰므로 새 DB 없이도 진행할 수 있다.
- [예전 스키마 스냅샷](../frontend/supabase/schema/README.md)은 기존 앱의 구조 자료다. 테이블 생성 순서가 맞지 않아 파일을 그대로 실행할 수 없고, 최신 음성 기준인 **최소 시간 없음·최대 60초**도 초기 구조에 다시 반영해야 한다.

## 기존 앱 구조를 읽는 작은 예

`사용자(users)`가 `가족방(rooms)`에 `참여(room_members)`하고, 그 방에 `추억(memories)` 1개를 남긴다. 다른 참여자가 그 추억에 `댓글(memory_comments)`을 달 수 있다. `사서함(heart_messages)`은 보내는 사람·받는 사람이 있는 별도 기록이다. 사진·음성 파일 자체는 Storage에, DB에는 파일의 위치와 길이 등을 저장했다. 이 관계는 **옛 앱의 코드와 SQL에서 읽은 사실**이며, 새 DB에 모두 필요하다고 확정한 설계는 아니다.

예를 들어 추억 한 건이 `room_id`를 갖는 이유는 어느 가족방의 글인지 연결하기 위해서다. 연결만으로 접근이 제한되지는 않는다. 누가 그 추억을 읽고 쓸지 정한 뒤 RLS(행 단위 접근 규칙)까지 맞춰야 한다. 기존 앱에서는 방 참여자가 추억을 읽고 작성자만 수정할 수 있게 했으나, 새 DB의 정책으로 채택할지는 검토가 필요하다.

## 함께 정할 순서

1. **첫 완료 범위:** 지금 필요한 것이 브라우저 데모 검증, 기존 앱의 추억·댓글·사서함 복구, 기존 앱 전체 복구 중 무엇인지와 그 이유를 듣는다. 데모 검증만 우선하면 새 DB는 당장 필요하지 않다.
2. **사용 장면과 접근:** 첫 범위의 기록을 누가 만들고, 누가 보며, 혼자 사용할 때 어떤 일이 가능한지 사용 장면으로 적는다. 사용자는 본인 기록에 반응할 수 있다고 이미 선택했다.
3. **표·연결·규칙:** 위 장면에 필요한 표와 필드, 파일 보관, RLS를 작은 예로 설명하고 사용자 선택과 AI 제안을 구분한다.
4. **검토 가능한 SQL:** 확정된 선택만 실행 가능한 초기 마이그레이션 초안에 옮기고 격리 환경에서 검사한다. 원격 DB 적용과 앱 동작 확인은 별도 단계로 기록한다.

**2026-09-26 후속 상태:** 위의 첫 질문 대기 표기는 이 작업판 작성 당시 상태다. 사용자는 이후 기존 앱의 성인 가입·방·초대·추억·댓글·사서함부터 복구하고, 추억에만 영상 1개를 다른 수단과 함께 담으며 파일 선택·앱 안 촬영을 모두 지원하기로 했다. 영상은 최소 시간 없이 최대 30초, 음성은 최소 시간 없이 최대 60초다. 50MB 초과 영상은 이유를 알려 재선택한다. 작성 당시 활성 참여자가 한 명인 추억은 첫 초대 전이든 다시 혼자가 된 때든 작성자만 볼 수 있고, 작성자가 삭제하면 연결 파일·댓글까지 완전히 지운다. 관계 유형·답장 잠금은 활성 기능에서 제거하되 자유 입력 호칭·과거 근거는 보존한다. 실제 만 14세 미만 가입은 보호자 확인 기능을 완성한 뒤에만 허용한다.

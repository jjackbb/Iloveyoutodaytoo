# 탈퇴 뒤 남은 파일 정리

대상 운영 DB: `wdzzianhfnupmfbjqqac`. `20260928000003_withdraw_storage_jobs.sql`부터 탈퇴 함수가 계정·방·추억을 지우기 **전에** 삭제 대상 Storage 객체를 `public.storage_deletion_jobs`에 기록한다. 앱은 탈퇴 직후 삭제를 시도하고, 실제 Storage 객체가 사라진 작업만 지운다. 계정이 이미 삭제된 뒤 남은 작업은 운영자가 재시도한다.

## 확인

Supabase SQL Editor에서 관리자 권한으로 실행한다. `object_name`은 개인정보가 담긴 경로일 수 있으므로 결과를 공개 문서나 로그에 붙이지 않는다.

```sql
select j.id, j.requested_by, j.bucket_id, j.object_name,
       j.created_at, j.attempts, j.last_error,
       (o.id is not null) as object_exists
  from public.storage_deletion_jobs j
  left join storage.objects o
    on o.bucket_id = j.bucket_id and o.name = j.object_name
 where j.reason = 'account_withdrawn'
 order by j.created_at;
```

`object_exists = true`인 행은 Supabase Storage 관리 화면에서 해당 버킷·경로를 확인하고 삭제한다. 삭제 전 `requested_by`의 Auth 계정이 실제로 없는지 확인한다. 이 작업표는 탈퇴 과정에서 생성된 경로이지만, 경로가 다른 이용자의 현재 기록에도 연결되어 있다면 삭제하지 말고 원인을 조사한다. 삭제 오류가 나면 `attempts`·`last_error`와 작업 시각을 기록하고 다음 점검 때 재시도한다. Storage 객체가 실제로 없어지기 전에는 작업표 행을 지우지 않는다.

오류를 남길 때는 확인한 작업 `id` 하나만 대상으로 다음 명령을 실행한다. 오류 설명에 파일 내용이나 비밀 키를 넣지 않는다.

```sql
update public.storage_deletion_jobs
   set attempts = attempts + 1,
       last_error = left('[실제 오류 요약]', 500),
       claimed_at = null
 where id = '[확인한 작업 id]'::uuid
   and reason = 'account_withdrawn';
```

Storage 삭제 뒤 다음 SQL로 확인된 작업만 정리한다. 결과가 0건이 될 때까지 정기적으로 점검한다. 점검 주기와 담당자는 운영자 지정 전이므로 가입 개방 전에 확정해야 한다.

```sql
delete from public.storage_deletion_jobs j
 where j.reason = 'account_withdrawn'
   and not exists (
     select 1 from storage.objects o
      where o.bucket_id = j.bucket_id and o.name = j.object_name
   )
returning j.id;
```

`memory_deleted`·`memory_updated` 작업도 같은 표에 남을 수 있다. 위 명령은 탈퇴 작업만 대상으로 한다. 계정이 살아 있다면 앱의 추억 삭제 재시도로 우선 처리한다.

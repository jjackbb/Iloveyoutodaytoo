## 검사와 남은 적용

- `npx tsc --noEmit --incremental false`와 변경한 TypeScript 파일 ESLint 통과. 데모 세 주소 HTTP 200은 이름표 수정 뒤 확인한 결과이며, 음성 정책 수정 뒤의 브라우저 동작 증거는 아니다.
- 사용자는 삭제된 기존 프로젝트 대신 `wdzzianhfnupmfbjqqac`를 지정하고 Codex MCP 연결·앱 환경 설정의 현 상태 확인을 요청했다. Codex 사용자 설정에 이 ID로 묶인 **읽기 전용 MCP 서버를 등록하고 OAuth 로그인을 완료**했다. 현재 대화의 도구 목록은 시작 시점 상태라 새 도구가 아직 보이지 않아 MCP를 통한 SQL·카탈로그 조회는 `NOT_RUN`이다. `frontend/.env.local`은 사용자가 새 URL과 두 키로 갱신했으며, URL과 두 JWT의 프로젝트 ID가 일치한다. 새 공개 키는 Auth 설정 요청 200, 임의의 잘못된 키는 401이었다. 새 서버 키로 공개 Data API의 경로 목록을 읽으면 루트 경로 1개뿐이고 `memories`·`memory_comments`·`heart_messages`는 없다. 공개 키로 세 테이블을 `limit=0` 조회한 결과 모두 404였고, `memories`는 `PGRST205`(스키마 캐시에서 테이블을 찾지 못함)다. 이는 **기존 앱의 세 테이블을 현재 API에서 사용할 수 없다는 증거**다. 실제 DB 카탈로그와 데이터 복원 여부는 별도 확인이 필요하다. [DB 변경 SQL](../frontend/supabase/schema/12_voice_no_minimum.sql)은 **로컬 준비**이며 원격 적용·앱 배포·짧은 녹음 저장은 `NOT_RUN`이다. 키 값은 기록하지 않았다.
- 사용자는 삭제된 이전 프로젝트의 별도 백업이 없다고 밝혔다. [스키마 스냅샷](../frontend/supabase/schema/README.md)은 데이터·Storage 파일을 담지 않고, `01_tables.sql`의 첫 테이블부터 아직 생성되지 않은 `users`를 외래 키로 참조한다. 그러므로 번호대로 그대로 실행하는 복구 절차는 성립하지 않는다. 기존 앱을 다시 쓰려면 새 DB 카탈로그를 읽고 실행 가능한 초기 마이그레이션으로 재구성해 별도 환경에서 검증해야 한다. 이는 Codex의 기술 판단이며 사용자 복원 결정·원격 적용은 아니다.
- 사용자는 **과거 데이터 복구는 필요 없다고 확인**했다. 따라서 다음 판단 대상은 새 프로젝트에서 기존 앱의 빈 DB 구조·권한·Storage 설정을 어디까지 다시 만들지다. 과거 사용자 기록을 가상 데이터로 채워 복구된 것처럼 표시하지 않는다. 현재까지 원격 스키마 복원·앱 동작 확인은 `NOT_RUN`이다.
- 이후 같은 대화에서 새 읽기 전용 MCP 도구가 노출됐다. 프로젝트 URL 조회는 `https://wdzzianhfnupmfbjqqac.supabase.co`를 반환했고, `list_tables(public)` 결과는 빈 목록이었다. SQL 카탈로그 조회는 `public` 테이블 0개, `auth.users` 행 0개, Storage 버킷 0개를 확인했다. 위의 “MCP 조회 `NOT_RUN`/카탈로그 미확인” 문장은 이 조회 이전 시점의 기록이다. **현재 확인된 상태는 빈 `public` 스키마**이며, 원격 쓰기·복원·앱 동작 검증은 여전히 `NOT_RUN`이다.

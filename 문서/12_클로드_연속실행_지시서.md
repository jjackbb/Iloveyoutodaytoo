기준일: 2026-09-26. 사용자는 Codex와 함께 정한 DB·영상 계획을 Claude가 구현하고, [PLAN](../PLAN.md)의 **인터뷰안 작성 이외** 작업을 순서대로 이어가도록 요청했다. 이 문서는 실행 지시와 다음 세션의 시작점이다. 문서 작성 자체는 SQL 실행·앱 구현·검증 완료가 아니다.

## 2. 지금 확정된 DB·영상 계약 — 첫 큰 작업

**완료선:** 새 Supabase 프로젝트 `wdzzianhfnupmfbjqqac`의 빈 상태를 전제로, 기존 앱의 성인 가입 → 가족방 만들기·기존 초대 링크로 입장 → 추억·댓글·사서함 흐름과 **추억 영상 작성·열람**을 로컬에서 구현·검증한다. 과거 데이터 복원은 불필요하다. 이 단계는 원격 프로젝트에 SQL을 적용하거나 앱을 배포하는 단계가 아니다. 포트폴리오의 `/demo`는 브라우저 저장소를 계속 사용한다.

### 데이터와 권한

1. `frontend/supabase/schema/`의 옛 파일은 구조 자료로 읽는다. `01_tables.sql`에는 생성 순서 오류가 있고 `12_voice_no_minimum.sql`은 삭제된 옛 DB를 전제로 하므로 새 DB에 순서대로 실행하지 않는다. `frontend/supabase/migrations/`에 빈 DB용 초기 마이그레이션을 새로 만든다. 앱이 현재 참조하는 활성 표·함수·버킷과 초대 링크 계약을 대조해 누락 없이 재구성한다. 새 프로젝트 ID와 로컬 URL을 혼동하지 않고 키는 기록·출력하지 않는다.
2. `rooms`·`room_members`·`invitations`와 `memories`·`memory_photos`·`memory_comments`·`heart_messages` 및 활성 부속 기능을 현재 앱과 맞춘다. **관계 유형**과 **답장 잠금**의 활성 DB 객체·코드·현재 명세는 제거한다. 초대장의 `relationship_label` 같은 자유 입력 호칭과 역사 자료는 유지한다. 사서함의 기존 문자·음성 처리 경로를 보존하며, 사서함 영상 작성은 추가하지 않는다.
3. 추억을 저장하는 **그 순간** 활성 참여자가 한 명이면 작성자 전용, 둘 이상이면 방 공유로 표시하고 이후 바꾸지 않는다. 첫 초대 전과, 가족이 모두 떠나 다시 혼자 쓴 기간에 동일하게 적용한다. 공유 시기에 쓴 추억은 나중에 들어온 활성 참여자도 읽을 수 있다. 추억·사진·영상·음성·손글씨·댓글·반응·알림·위젯·서명 URL을 같은 가시성으로 묶는다. 방 생성·초대 수락·추억 저장이 동시에 일어나도 분류가 뒤집히지 않도록 DB에서 직렬화한다.
4. 현재 `public.users`는 방 참여자에게 보호자 연락처·생년월일 등을 노출할 수 있다. 이름·프로필 사진 등 방에서 필요한 정보와 본인만 읽을 계정·보호자 정보를 나눈다. Storage는 경로의 방 ID만으로 읽기를 허용하지 않는다. 업로드 소유자와 연결 기록을 검증하고, 상대는 자신이 읽을 수 있는 기록에 연결된 파일만 읽거나 서명할 수 있게 한다. 익명·작성자·새 참여자·떠난 참여자의 우회 접근을 확인한다.
5. 만 14세 미만 정책과 사용자가 삭제할 때까지 보관하는 정책을 유지한다. `guardian_verifications` 등 구조와 합성 검사는 준비하되, **실제 보호자 확인이 끝나기 전 미성년 가입은 막는다.** 체크박스나 미검증 전화번호를 확인 완료로 취급하지 않는다. 사용자가 추억에서 ‘삭제’를 누르면 추억·연결 파일·댓글을 완전히 제거하고 모두의 접근을 막는다. DB와 Storage 중 하나가 실패하면 성공이라고 알리지 않고 남은 작업을 재시도 가능하게 기록한다.

### 영상·음성 화면

1. 기존 앱의 추억 작성에 네 번째 수단 `영상`을 넣는다. 파일 선택과 앱 안 촬영을 모두 제공한다. 한 추억에 영상은 **최대 한 개**이며 손글씨·목소리·사진과 함께 저장할 수 있다. 영상 하나만으로도 작성 가능하다. 선택·촬영·미리보기·제거·재시도·저장 후 재생과 수정·삭제 흐름까지 연결한다.
2. 영상 길이는 **최소 없음·최대 30초**, 음성은 추억·댓글·사서함 모두 **최소 없음·최대 60초**다. 빈 파일은 거절한다. 30초 이하라도 영상이 50MB를 넘으면 업로드 전에 이유를 알려 다시 선택·촬영하게 한다. 자동 압축은 이번 범위가 아니다. 화면의 실제 길이 검사와 DB의 경로·길이 짝 및 범위 제약을 맞춘다.
3. 촬영 권한 거부, 지원하지 않는 파일, 업로드 중단, 저장 재시도와 고아 파일 정리를 처리한다. 이 범위의 UI는 기존 디자인 결정과 `frontend/CLAUDE.md`의 디자인 지침을 따르되, 기존 앱 영상 작성에 필요한 변경과 포트폴리오 데모의 대표 시안 선택을 혼동하지 않는다.

### 로컬 검증과 보고

- 사용자가 고른 방식은 Docker 호환 실행기와 Supabase CLI를 준비해 **격리 로컬 DB**를 시험하는 것이다. 현재 컴퓨터의 설치 상태를 먼저 다시 확인한다. 로컬 초기화·마이그레이션 재실행, 생성 타입 반영, 앱 타입 검사·빌드, DB/RLS 검사, 실제 브라우저 작성·재생을 순서대로 한다.
- 성인 합성 계정 A·B·C와 익명 사용자로 초대 전 비공개, 공동 작성, 다시 혼자 작성, 댓글·사서함, 자기 추억 반응, 개인 정보 차단, Storage 직접 경로·서명 차단을 검사한다. 삭제 성공과 DB·Storage 한쪽 실패 후 재시도도 검사한다. 0~30초 영상/초과 영상, 50MB 초과 파일, 0~60초 음성/초과 음성, 촬영 권한 거부를 분리해 기록한다. 합성 검사와 실제 브라우저 검사는 서로 다른 근거다.
- 실패하면 해당 실패가 의존하는 다음 작업을 중단하고 원인을 고친 뒤 필요한 범위만 재검사한다. **원격 SQL 적용·실제 미성년 가입·앱 배포·실사용자 결과는 이번 단계 `NOT_RUN`**이라고 남긴다. 완료 뒤 새 [작업 인수인계](인수인계/README.md)를 만들고 PLAN·DB 작업판·개인비서 기록의 확정/구현/검증 상태를 갱신한다.

## 4. 큰 작업마다 다른 Claude 세션에 넘기는 법

- A의 DB, A의 영상, B, C, D, E, F, G, H를 각각 큰 작업 단위로 본다. 단위가 끝나거나 사용자 판단 때문에 멈추면 **그 자리에서** `문서/인수인계/YYYY-MM-DD_작업명.md`를 새로 만든다. 기존 인수인계를 덮어쓰지 않는다. [양식과 작성 규칙](인수인계/README.md)을 따른다.
- 인수인계에는 기준 시각·담당 범위, 실제 변경 파일, 실행한 검사와 결과, `NOT_RUN`/막힘, 사용자가 확정한 것과 아직 묻지 않은 것, 다음 세션의 **첫 명령 또는 첫 읽기 파일**, 다른 세션이 만지는 파일을 적는다. 필요한 새 사용자 질문은 1~3개로 모아 마지막에 제시한다.

기존 `/rooms/[roomId]/compose`를 지우지 않고 남겨, 되돌릴 때 한 줄만 바꾸면 되게 한다.

## 영상 — 무엇을 만드나

**비트윈 방식.** 받아서 재생 버튼을 누르는 것이 아니라, **GIF처럼 그 자리에서 바로 돈다.**

- 피드 카드 안에서 **소리 없이 자동 재생 + 반복**, 화면에 보일 때만 (`IntersectionObserver`).
  스크롤로 벗어나면 멈춘다 — 안 그러면 데이터와 배터리를 먹는다.
- 누르면 전체화면에서 소리와 함께 처음부터.
- 길이 **최대 1분**. 답장(댓글)에도 쓸 수 있다.

### ⚠ 50MB 벽

Supabase **무료 플랜은 파일 하나당 50MB가 상한**이다(Pro는 500GB). 문서에서 확인했다.
아이폰 1080p가 초당 약 1MB라 **1분이면 50MB를 넘길 수 있다.**

→ **길이는 1분까지 받되, 실제로 막는 것은 50MB.**
   넘으면 "영상이 너무 커요. 짧게 잘라 올려주세요"로 안내한다.
   진짜로 1분을 보장하려면 Pro 플랜이 필요하다 — 보관 정책을 정할 때 같이 본다.

`media` 버킷은 이미 `video/mp4`·`video/webm`·`video/quicktime`을 받고 상한이 50MB다.
DB에도 `media_type: 'photo' | 'video'` 가 있다. **바닥은 깔려 있다.**

## 알림 — 웹푸시 먼저

카카오 알림톡은 사업자등록증 + 발신프로필 + 템플릿 심사가 필요해 수일~수주가 걸린다.
웹푸시는 **계약도 등록도 필요 없고 무료**다. 먼저 붙여 동작시키고, 알림톡은 나중에 얹는다.
단, **아이폰은 홈 화면에 추가(PWA)해야 받는다** — 이 안내를 화면에 둔다.

## 카카오 로그인 — 사업자 등록이 필요 없다

Supabase가 `kakao` 제공자를 기본 지원한다(공식 문서 확인).
이메일 동의항목(`account_email`)은 Biz App(사업자 등록)이 필요하지만,
Supabase에 **"Allow users without an email"** 옵션이 있어 **등록 없이 출시할 수 있다.**

- 사용자가 할 일: 카카오 개발자 포털에서 앱 생성 → REST API 키 + Client Secret
- 우리가 할 일: `/auth/callback` 라우트 + `/start`의 [준비 중] 버튼 연결
- `/start`에 자리가 이미 잡혀 있어 **화면은 안 바꾼다**

## 오늘의 질문 — 84줄이 죽어 있었다

`lib/prompts.ts`(84줄)를 **아무 화면도 쓰지 않는다.** DB 컬럼(`heart_messages.prompt_used`)과
사서함의 표시 코드는 있는데, 정작 **질문을 골라주는 화면이 없다.**
`prompt_used`가 `heart_messages` 컬럼이므로 **사서함 '마음 보내기'에 붙인다.**

## 아이폰 햅틱 — 앱으로 갈 때

## 1. 만 14세 미만 — 계속 받는다 (차단하지 않는다)

§22조의2)일 뿐이다. 대부분의 서비스가 가입을 막는 건 법 때문이 아니라 **동의 절차를
만들기 싫어서** 택하는 우회로다.

**우리는 이미 그 절차를 만들어놨다:**
- `signup-form.tsx:49` — 생년월일 입력 즉시 `needsGuardianConsent()` 판별
- 미만이면 보호자 성함·연락처·동의 확인란이 나타남
- `auth.ts:253` — 서버에서 재검사, 하나라도 비면 거절
- `terms.md 제5조`, `privacy.md 제9조`에 절차 문서화 완료

서비스 성격상으로도 막을 이유가 없다. 가족 앨범방이고, **손주가 할머니에게 음성을
보내는 것**이 핵심 장면에 가깝다. 유해 콘텐츠·결제·낯선 사람 없음. 방은 초대로만 들어온다.

> ⚠️ `birth_date`를 NOT NULL로 두는 이유는 **"아이를 걸러내려고"가 아니라
> "보호자 동의 칸을 띄울지 판단하려고"** 다. 이걸 풀면 보호자 동의 분기가 통째로 죽는다.
> 소셜 로그인을 붙일 때도 추가 정보 화면에서 생년월일을 받아 **기존 보호자 동의 블록을
> 그대로 재사용**한다. 새로 설계할 것 없음.

## 2. 보호자 문자 확인 — 추가한다 (국내 SMS, Firebase 아님)

**현재 구멍:** `guardian_phone`을 받아 저장만 하고 **그 번호로 아무것도 보내지 않는다**

`terms.md:53`이 이 한계를 정직하게 명시하고 있다.

**Firebase Phone Auth를 쓰지 않는 이유 3가지:**

3. **발신번호 사전등록제** — 전기통신사업법상 국내 발송은 발신번호 사전 등록 필요.

**채택: 솔라피(SOLAPI) 등 국내 SMS**

- 휴대폰 로그인 붙일 때 **같은 연동을 재사용**
- 비용 감각: 하루 10명이어도 월 300건 ≈ 5,400원. 무시할 수준

## 3. GA4 계측 도입 — 포트폴리오용 (Firebase SDK 아님)

목적: 유저 테스트에서 **이탈 지점·병목·자주 쓰는 지점**을 숫자로 파악하고
"이렇게 개선했습니다"까지 쓰는 것. 기획자 포트폴리오.

**현재 계측이 전무하다** (gtag·firebase·posthog 전부 없음 — grep 확인).

**도구: `@next/third-parties/google` (GA4 직접).** 웹에서 Firebase Analytics는 곧
GA4다. 같은 속성에 같은 데이터가 들어간다. Next.js 공식 컴포넌트가 가볍고 간단하며,
**나중에 앱화할 때 Firebase SDK를 추가하면 같은 GA4 속성에 붙는다.** 되돌릴 수 있는 결정.

**⚠️ GA4 데이터 보관 기간 기본값이 2개월이다. 관리 > 데이터 설정에서 14개월로 바꿀 것.**
안 바꾸면 3개월 뒤 포트폴리오 쓸 때 데이터가 사라져 있고, GA4는 소급 복구해주지 않는다.

**무료 한도** (우리 규모에서 닿을 일 없음): 이벤트 이름 500개, 이벤트당 파라미터 25개,
커스텀 디멘션 이벤트 50 + 유저 25.

### 이벤트 초안 (이름·파라미터 확정은 기획자 몫)

**A. 가입 이탈**
`start_view` → `signup_begin` → `signup_field_error`(`field`) → `signup_complete`

**B. 초대 → 구성원**
`invite_open` → `invite_signup_complete` → `first_reply_done`

**C. 몽실이 작성 ★ 포트폴리오 주인공**

### 순서 — 계측이 몽실이보다 먼저다

**GA4는 소급 집계가 안 된다.** 이벤트를 심기 전 행동은 영원히 알 수 없다.
몽실이를 먼저 붙이면 **"개선 전" 숫자가 존재하지 않게 되어** 포트폴리오 서사가 빈다.

```
1. 계측 + 보호자 문자 (동시 진행)   ← 지금
2. 기존 작성화면으로 유저테스트 1차   ← "개선 전" 확보
3. 몽실이 붙이기
4. 유저테스트 2차                   ← "개선 후"
5. 비교 + 개선 서사
```

**A/B(절반 기존/절반 몽실이)는 하지 않는다.** 유저 테스트 규모(수십 명)에서는
통계적으로 아무 말도 못 한다. **순차 비교 + 정성 인터뷰**가 이 규모에서 정직한 방법이고
포트폴리오에서도 더 신뢰를 준다.

## 4. DB는 Supabase 유지 — Firebase로 옮기지 않는다

"Supabase는 SQL을 직접 짜야 하니 Firebase가 포폴·성장에 낫다"는 조언이 있었으나,
**서로 무관한 두 가지를 섞은 말이다.**

| | 역할 | 우리 선택 |
|---|---|---|
| Firebase **Analytics** (=GA4) | 행동 계측 | ✅ 쓴다 |
| Firebase **Firestore/Auth** | 백엔드·DB | ❌ Supabase 유지 |

**Analytics를 쓰려고 DB를 옮길 필요가 없다.** GA4는 프론트엔드에 붙고 백엔드가 뭐든
상관하지 않는다. Supabase + GA4는 완전히 흔한 조합이다.

1. **이미 다 만들었다** — 21개 테이블, RLS, 트리거, 마이그레이션. 이전은 전면 재작성
2. **SQL은 기획자에게 무기다** — 채용 우대사항. Firestore는 NoSQL이라 SQL을 못 배운다.
   게다가 GA4 심화 분석은 결국 **BigQuery(SQL)** 로 한다
3. **우리 데이터는 관계형이다** — 방–구성원–메시지–답장. *"이 방 구성원 중 최근 7일
   답장 안 한 사람"* 이 Supabase에선 SQL 한 줄, Firestore에선 비정규화 문서 숙제가 된다

**포폴에서 더 강한 구성:** GA4만 붙인 포폴은 흔하다. GA4는 우리 DB를 모르고 Supabase는
이탈을 모른다. 둘을 잇는 게 실력이다 —
> *"던지기까지 간 사람 중, 실제로 답장을 받은 사람의 비율"*

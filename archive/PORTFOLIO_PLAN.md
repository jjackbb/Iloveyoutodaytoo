## 1. 결론과 확정된 범위

**기능을 더 늘리기보다, 기존 기능으로 서버 없이 체험할 수 있는 핵심 흐름을 완성하고 기획 판단의 근거를 남긴다.**

서비스가 해결하려는 문제와 이 프로젝트의 완료 목표를 나눈다.

| 구분 | 내용 | 근거 수준 |
|---|---|---|
| 서비스 목표 | 따로 사는 자녀와 부모가 부담 없이 마음을 표현하고, 남긴 마음을 다시 볼 수 있게 한다 | 기존 PRD의 문제·가치 정의. 효과가 입증됐다는 뜻은 아님 |
| 프로젝트 목표 | 체험 가능한 데모와 문제 → 선택 → 검증 → 개선을 설명하는 포트폴리오 사례를 완성한다 | 2026-09-22 사용자 지시 |
| 전달 방식 | **브라우저 데모 중심, 안드로이드 앱은 보조 자료** | 2026-09-22 사용자가 선택 |
| 백엔드 | Supabase 신규 연결·복구·추가 연동은 보류. 기존 코드·스키마·과거 검증 기록은 보존 | 사용자 지시를 현재 구조에 적용 |
| 이번 실행 범위 | 로컬 자료·코드 분석, 기본 검사, 계획 문서 작성 | 사용자 요청 |

브라우저 데모는 포트폴리오 체험 수단이다. 기존 서비스를 정식 웹 서비스로 출시한다는 결정까지 포함하지 않는다. 앱 삭제, 운영 DB 변경, 배포, 커밋·푸시는 이번 작업에 포함하지 않았다.

## 3. 포트폴리오 관점의 판단

**강점:** 제품 선택의 이유가 남아 있다. 답장을 강제하던 잠금을 제거한 결정, 음성 필수를 해제한 결정, 손글씨를 획 좌표로 저장해 쓰는 과정을 재생하게 한 결정은 설명 가능한 기획 사례다. 다만 사용자 행동이 실제로 달라졌는지는 별도 근거가 필요하다.

**가장 큰 빈칸:** “카카오톡이나 사진 앨범 대신 이곳을 사용할 이유”와 “부담 없이 반복해서 사용할 수 있는가”를 확인할 관찰이다. 화면 수나 백엔드 연결 여부만으로 이 빈칸이 채워지지는 않는다.

이번에는 두 가지를 검증 질문으로 둔다.

1. **표현 부담:** 앨범방의 선택형 표현 수단이 첫 마음 남기기에 도움이 되는가? 사서함의 음성 필수는 누구에게 부담이 되는가? ‘목소리 중심’이라는 현재 소개 문구가 손글씨·사진 경로를 가리지 않는가?
2. **받는 쪽 부담:** 숫자 배지와 톡톡을 반가운 신호로 읽는가, 밀린 답장으로 읽는가? 기존 “초대한 관계라 부담·스팸이 없다”는 판단은 검증할 가설이며 확정 사실이 아니다.

숫자 배지를 지금 임의로 폐기하거나 두 작성 경로를 합치지 않는다. 사용자가 실제로 혼동·압박을 겪는 관찰이 나오면 해당 결정을 다시 검토한다. 단일 세션 테스트로 장기 관계 개선이나 재방문 효과를 판정하지 않는다.

## 4. 제안하는 데모 범위

브라우저 중심이라는 방향은 확정됐다. 아래 세부 범위와 기술 방식은 **AI의 실행 설계안**이며 구현 완료나 별도 사용자 승인으로 기록하지 않는다.

### 반드시 완성할 하나의 흐름

**소개 → 데모 시작 → 가족 앨범방 → 손글씨 또는 음성/사진으로 마음 남기기 → 등록한 추억 열기·재생 → 부모 시점으로 전환 → 좋아요로 반응 → 쌓인 추억 다시 보기.**

- 자녀·부모 두 명의 가상 인물과 앨범방 하나를 기본 제공한다. 실제 가입 없이 시작한다.
- 첫 화면에 “가상 가족으로 체험하는 데모예요. 내용은 이 브라우저에만 저장돼요”라고 안내한다.
- 역할 전환은 데모 도구 영역에 두고 실제 서비스의 계정 기능처럼 표현하지 않는다.
- 역할을 바꿔 보는 것은 한 브라우저의 시뮬레이션이다. 다른 사람의 기기로 전송되거나 두 기기가 동기화되는 기능은 아니다.
- 핵심 표현인 손글씨 작성과 타임랩스는 직접 체험 가능하게 한다. 음성·사진은 기존 부품을 재사용하고, 권한 없이도 손글씨 또는 제공된 예제로 흐름을 끝낼 수 있게 한다.
- “작년 오늘” 등 예시 기록은 가상 데이터라고 표시한다. 실제 사용 기간·실적으로 해석되지 않게 한다.

| 데모 홈 | `/demo` | 역할·가족방·예시 추억 확인 | 초기 로딩, 저장소 읽기 실패, 초기 상태 복원 |

| 작성 | `/demo/rooms/family/compose` | 손글씨/음성/사진 중 하나 이상 → 로컬 저장 → 상세 | 빈 입력, 녹음 권한 거부, 저장 실패, 중복 누름, 작성 중 이탈 |
| 상세 | `/demo/rooms/family/memories/[id]` | 손글씨·음성 재생, 좋아요, 역할 전환 후 같은 기록 확인 | 잘못된 ID, 지원하지 않는 오디오, 손상된 자료, 재생 실패 |
| 데모 도구 | 공통 영역 | 가상 인물 전환, 예시로 초기화 | 초기화 전 삭제 범위 안내·확인, 실패 시 기존 상태 유지 |

실패 시 원칙: 저장 완료 전 성공 안내를 띄우지 않는다. 저장 실패 시 입력을 보존한다. 마이크 권한이 없어도 다른 표현 수단으로 완료할 수 있어야 한다. 두 번 눌러도 같은 기록이나 좋아요가 중복되지 않아야 한다.

모바일 폭의 실제 사용 흐름과 데스크톱의 포트폴리오 열람을 모두 확인한다. 예쁜 목업 테두리보다 글자·버튼·키보드·스크롤이 정상적으로 동작하는 것이 먼저다.

## 6. Supabase 없이 데모를 만드는 기술 설계

**추천: 기존 Next.js 프로젝트 안에 `/demo` 경로와 로컬 데이터 처리를 추가한다.** 전체 앱을 정적 페이지로 전환하거나 모든 서버 액션을 다시 만드는 일은 이번 목표에 필요하지 않다.

### 진입과 데이터 경계

1. `proxy.ts`에서 정확히 `/demo` 또는 `/demo/` 하위 경로를 식별하고, 브라우저 차단과 Supabase 클라이언트 생성 **이전**에 데모 분기를 끝낸다. `/demography` 같은 다른 경로를 포함하지 않게 한다.
2. `/welcome`을 서버와 무관한 체험 안내로 정리한다. 그 경로 역시 Supabase 초기화 전 통과해야 환경변수 없이 안내가 열린다. 공용 법적 안내를 유지한다면 데모에서 그 링크까지 열리는지 함께 확인한다.
3. 데모의 화면은 고정 예시 자료와 로컬 저장소만 읽는다. `requireUser()`, 실제 서버 액션, Storage 서명 URL을 데모에서 호출하지 않는다.
4. 기존 서비스의 인증·권한·실제 데이터 경로는 보존한다. 사용자 정보나 요청 매개변수로 운영 계정이 된 것처럼 처리하지 않는다.
5. 루트 레이아웃의 `SignupBeacon`, `NativeBridge`, GA 주입도 점검한다. 데모 이벤트를 가입·운영 성과로 보내지 않고, 앱 WebView로 데모를 열어도 위젯 토큰 발급이 실행되지 않게 한다.

### 부품 재사용 범위

- **바로 재사용 검토:** `HandwritingPad`, `HandwritingView`, `VoiceRecorder`, `VoicePlayer`, 기본 버튼·필드. 녹음기는 업로드 대신 Blob을 부모에게 전달하는 구조다.
- **주소 연결 변경:** `HandwritingPlayer`는 JSON 주소를 받는다. 예시 JSON 또는 로컬 Blob 주소를 사용할 수 있도록 연결한다. 새로고침 후에는 저장한 Blob/JSON에서 주소를 다시 생성한다.
- **분리가 필요한 부분:** `RoomCard`, `MemoryCard`는 props를 받아도 내부 버튼이 실제 서버 액션을 호출하고 링크가 `/rooms/*`로 고정돼 있다. 겉모습만 재사용하면 실제 서버로 새어 나간다. 데모에서 필요한 표시 부분과 동작 콜백·이동 주소를 분리한다.
- 전체 27개 화면을 추상화하지 않는다. 데모 주 흐름에서 필요한 부품에 한해 분리하고 기존 경로의 기본 동작이 유지되는지 확인한다.

### 로컬 저장 계약

추천 저장소는 **IndexedDB**다. 손글씨 JSON·녹음 Blob·사진 Blob을 다루고 새로고침 후 다시 열 수 있도록 한 저장 계층에 모은다. 별도 서버·새 데이터베이스 계정은 필요 없다.

| 데이터 | 최소 내용 |
|---|---|
| 데모 상태 | 데이터 버전, 현재 가상 인물, 예시 초기화 여부 |
| 앨범방 | 고정 ID, 이름, 구성원 ID, 커버 |
| 추억 | ID, 작성자, 방 ID, 시각, 문구, 손글씨 JSON·미디어 참조 |
| 반응 | 추억 ID + 가상 인물 ID로 유일한 좋아요 |
| 미디어 | 로컬 ID, Blob, 종류, 재생 길이·필요한 표시 정보 |
| 읽음 상태 | 숫자 배지를 구현할 경우에만 인물별 확인한 추억 ID |

저장 계층의 최소 동작은 초기 예시 불러오기, 추억 저장·조회, 좋아요 전환, 역할 전환, 데모 초기화다. 저장은 기록과 미디어가 일치하도록 처리하고 실패하면 성공 상태로 바꾸지 않는다. UI는 저장 성공 또는 사용자가 이해할 오류를 받는다.

- 사진·음성을 큰 Base64 문자열로 `localStorage`에 넣거나 Blob 임시 주소 자체를 영구 저장하지 않는다.
- 로컬 저장소 사용이 불가능하면 “이 환경에서는 저장할 수 없음”을 안내하고 초기 예시를 읽을 수 있게 한다. 재시도·초기화 방법을 제공한다.
- 초기화는 이 데모의 저장소·임시 미디어·표시용 주소만 정리한다. 도메인의 다른 저장 정보나 기존 인증 쿠키까지 지우지 않는다.
- 저장은 **현재 브라우저·현재 기기 한정**이다. 영구 보관·백업·기기 간 동기화를 약속하지 않는다. 웹 페이지를 여는 데 필요한 서버까지 없어지는 것은 아니므로 오프라인 앱으로 소개하지 않는다.
- 숫자 배지는 넣는다면 “현재 인물 외의 작성자가 남겼고, 현재 인물이 아직 확인하지 않은 추억 수”로 정의한다. 전체 게시물 수를 새 마음 수로 대신 쓰지 않는다. 부담감 검증에 따라 표시 방법은 재검토할 수 있다.

## 8. 검증 과업과 포트폴리오 근거

### 데모 기술 확인 — 구현 후 실행, 현재 모두 NOT_RUN

수정 부위의 lint·타입·빌드와 위 과업을 확인한다. 새 결함이나 변경 없이 검사 범위를 반복해서 넓히지 않는다. 순수 계산보다 저장 후 재열람·초기화·서버 요청 경계를 우선 검증한다.

### 사용자 과업 — 추천 설계, 모집·실행은 NOT_RUN

처음에는 자녀와 부모 **2~3쌍**을 대상으로 소규모 사용성 점검을 제안한다. 두 역할의 막힘을 각각 발견하려는 규모이며 시장 수요·통계적 효과를 추정할 표본이 아니다. 실제 모집 가능 인원에 맞춰 정한다.

1. 설명을 최소화한 상태에서 가족에게 마음을 하나 남기게 한다. 첫 클릭, 수단 선택, 멈춤, 도움 요청을 기록한다.
2. 부모 역할이 남겨진 마음을 찾고 재생·반응하게 한다. 역할을 바꿔 조작하는 기술 시뮬레이션과 실제 부모 참여를 구분한다.
3. 이전 추억을 다시 찾게 한다. 찾는 단서와 알림 숫자의 의미를 먼저 본인의 말로 설명하게 한다.
4. “최근 가족에게 마음을 전했던 실제 상황”과 비교해 이 서비스가 필요했던 순간·불필요한 순간을 묻는다. “쓸 것 같다”만으로 반복 사용을 확인했다고 기록하지 않는다.

진행자가 전송·로그인 성공을 연기해야 하는 부분은 데모 제약으로 기록한다. 두 기기 전달·설치·푸시·실제 재방문은 이 테스트가 검증할 수 없다.

측정은 GA4 연결 없이 관찰 기록으로 시작한다.

| 기록 | 정의 |
|---|---|
| 무도움 과업 완료 | 과업을 시도한 참여자 중 진행자의 조작·경로 힌트 없이 끝낸 사람 수. 역할별 `n/N`으로 표시 |
| 도움·막힘 | 과업별 멈춘 화면·시도·안내·발화. 기술 실패인지 의미 이해 실패인지 구분 |
| 표현 수단 | 선택한 수단과 당사자가 말한 이유. 화면에 먼저 보여서 고른 것인지도 확인 |
| 부담 | 답장·알림을 어떻게 해석했는지 원문과 행동. AI의 해석을 별도 표시 |
| 전후 비교 | 개선 전후 같은 과업의 관찰. 같은 사람이 재참여했다면 학습 효과를 한계로 기록 |

자동 이벤트가 필요해지면 `demo_memory_saved`, `demo_memory_played`, `demo_reaction_changed`, `demo_reset`처럼 운영 이벤트와 분리한다. 저장 성공·실제 재생 시작·실제 반응 변경·초기화 성공 시에만 발생시키고 화면 재렌더링은 중복으로 세지 않는다. 테스트 회차·역할·표현 종류만 기록하며 음성·사진·문구 내용은 이벤트에 담지 않는다. 수집 동작 확인 전에는 숫자를 결과로 사용하지 않는다.

## 9. 최종 포트폴리오 구성과 완료 기준

설명 순서는 **누구의 어떤 문제 → 기존 대안의 빈틈과 근거 → 비교한 해결책 → 선택과 포기 → 데모 → 실제 관찰·개선 → 한계**다. 기능 목록을 본문 중심으로 두지 않는다.

남길 산출물:

- 설치·가입 없이 열 수 있고 초기화 가능한 브라우저 데모
- 핵심 흐름의 화면과 짧은 시연 영상, 실행 안내
- 표현 부담·양방향 반응·쌓임을 연결한 기획 사례 문서
- 사용자 판단 / 팀 기여 / AI가 구현·정리한 일의 구분
- 테스트 원자료·개선 전후 근거 또는 미실시 이유와 다음 검증 설계

**검증을 포함한 사례의 완료 조건:** 핵심 기술 과업 통과, 목표 사용자 관찰과 최소 한 차례 개선·재확인, 주장마다 근거·제약 표시. 모집이 어려우면 데모·설계 포트폴리오로 먼저 묶을 수 있으나, 사용자 가치 검증은 `NOT_RUN`으로 남기고 검증 완료 사례로 소개하지 않는다.

| 지금 가능한 표현 | 아직 근거가 부족한 표현 |
|---|---|
| 표현 부담을 줄이려 음성 필수·답장 잠금을 재검토한 설계와 코드가 있다 | 표현 부담이 실제로 감소했다 |
| 손글씨 획·시간을 저장해 재생하는 코드가 있다 | 목표 사용자가 현장감을 느낀다는 것이 확인됐다 |
| 과거 문서에 특정 환경의 앱 링크 검증이 기록돼 있다 | 현재 앱·위젯·푸시가 모두 실기기에서 작동한다 |
| 이번에 lint·타입·Webpack 빌드를 확인했다 | 데모·운영 서비스가 현재 정상 작동한다 |
| 브라우저 데모를 만들기로 방향을 정하고 설계했다 | 브라우저 데모가 완성됐다 |

Supabase 연결을 다시 검토할 조건은 **서로 다른 기기에서 실제로 주고받는 테스트**, 실제 초대·가입 검증, 지속 사용·보관 검증이 필요해지는 때다. 포트폴리오 화면을 더 늘리기 위한 이유만으로 재개하지 않는다.

# 오늘도사랑해 이식 오케스트레이터

## 이 하네스가 막으려는 것

프로토타입은 **잔여데이터** 때문에 폐기됐다. 19개 화면이 한 DOM에 살아 있고 JS가
보이기/숨기기만 해서, 화면을 나가도 이전 값이 남아 다음에 튀어나왔다.

디자인은 멀쩡했다. 그래서 **모양과 구조는 가져오되, 그 오류를 만든 JS 상태 기계는
한 줄도 가져오지 않는다.** 이 하네스의 모든 관문이 그걸 지키려고 있다.

## 실행 모드

**서브 에이전트 모드.** (이 빌드에 `TeamCreate`가 없어 에이전트 팀은 쓸 수 없다.
대신 `SendMessage`로 이미 띄운 에이전트를 컨텍스트 유지한 채 다시 부른다.)

모든 `Agent` 호출에 `model: "opus"`를 명시한다.

## Phase 0 — 어디서부터 시작할지 정한다

먼저 `_workspace/` 를 확인한다:

| 상태 | 모드 |
|---|---|
| `_workspace/` 없음 | **초기 실행** — Phase 1부터 |
| 있고, 사용자가 특정 화면 수정 요청 | **부분 재실행** — 그 화면만 Phase 3부터 |
| 있고, 사용자가 "이어서"/"다음 화면" | **이어가기** — `_workspace/PROGRESS.md`를 읽고 다음 화면부터 |
| 있고, 전제가 바뀜 (판정 변경 등) | **새 실행** — 기존을 `_workspace_prev/`로 옮기고 Phase 1부터 |

`_workspace/PROGRESS.md`에 화면별 상태를 기록한다 — 이게 세션이 끊겨도 이어갈 수 있게 한다.

## Phase 1 — 토큰 대조 (한 번만, 화면 작업 전에)

`prototype-extractor`를 불러 프로토타입 `<style>`의 여백·글자크기·모서리·그림자·전환을
`src/app/globals.css` 현재 토큰과 대조하게 한다.

**색은 대조 대상이 아니다** — 현재 값 고정이다 (WCAG AA 검증 통과).

산출물: `_workspace/00_token_diff.md` — **충돌하는 것만** 표로.
→ **사용자 승인 후** `globals.css`에 반영한다. 승인 없이 토큰을 건드리지 마라.

## Phase 2~ — 화면 하나씩 (반복)

순서: **홈 → 방 상세 → 사서함 → 마이 → 초대(링크/QR + 연락처) → 나머지**

부품은 화면 작업 중에 필요해질 때 뽑는다. 부품만 따로 다 만들어 놓고 화면에 붙이는
방식은, 실제로 어디에 쓰일지 모른 채 설계하게 되어 두 번 고치게 된다.

### 각 화면의 5단계

```
A. 추출   prototype-extractor       → _workspace/{screen}_spec.md
B. 이식   screen-porter             → src/ 코드 + {screen}_port.md
C. 검증   residue-qa ∥ prd-guard    → {screen}_qa.md, {screen}_prd.md   ← 병렬
D. 수정   screen-porter (SendMessage로 재호출)                          ← 최대 2회
E. 관문   verify.sh + 스크린샷 → 사용자 확인
```

**C를 병렬로 돌리는 게 이 하네스가 빠른 이유다.** 두 검증은 축이 다르다 —
`residue-qa`는 기술적 정확성, `prd-guard`는 기획 준수. 서로 기다릴 이유가 없다.

**속도를 더 내려면:** C가 도는 동안 다음 화면의 A(추출)를 미리 돌려도 된다.
추출은 앞 화면 결과에 의존하지 않는다.

### D의 상한이 2회인 이유

3회째에도 안 끝나면 그건 코드 문제가 아니라 **명세나 판정이 잘못된 것이다.**
계속 돌리지 말고 멈춰서 사용자에게 무엇이 막혔는지 보고하라.

### E — 사용자 확인을 건너뛰지 마라

`05_REDESIGN_PLAN.md`가 명시한다: **"화면 하나씩 캡처해서 보여드리고 넘어간다.
한꺼번에 다 바꿔놓고 확인받지 않는다."**

관문:
```bash
bash .claude/skills/residue-scan/scripts/verify.sh
```
통과 못 하면 다음 화면으로 넘어가지 않는다. 예외 없다.

## 에이전트 호출 형태

```
Agent(subagent_type: "prototype-extractor", model: "opus",
      prompt: "화면 `home`을 추출해 _workspace/home_spec.md 로 저장하라. …")

# 검증 둘은 같은 응답에서 동시에 (병렬)
Agent(subagent_type: "residue-qa", model: "opus", run_in_background: true, …)
Agent(subagent_type: "prd-guard",  model: "opus", run_in_background: true, …)

# 수정은 이미 띄운 이식가를 다시 부른다 — 컨텍스트가 유지돼 훨씬 빠르다
SendMessage(to: "screen-porter", message: "_workspace/home_qa.md 와 home_prd.md 의 지적을 …")
```

## 데이터 전달

파일 기반(`_workspace/`) + 반환값. 중간 산출물은 지우지 않는다 — 나중에
"왜 이렇게 했지"를 되짚는 근거다.

파일명: `{순번}_{화면}_{종류}.md` (예: `01_home_spec.md`)

## 에러 핸들링

| 상황 | 처리 |
|---|---|
| 에이전트 실패 | 1회 재시도. 또 실패하면 그 결과 없이 진행하되 **보고서에 누락을 명시** |
| 두 검증의 지적이 충돌 | 삭제하지 말고 **양쪽 출처를 함께 남긴다.** 사용자가 판단 |
| 명세 ↔ PRD 충돌 | **PRD가 이긴다.** 충돌 사실 보고 |
| PRD 문서끼리 충돌 | 판단하지 말고 양쪽 인용해 사용자에게 |
| 관문(verify.sh) 실패 | 다음 화면 금지. 원인 고칠 때까지 |
| 수정 3회째 | 멈추고 보고 — 명세/판정 문제다 |

## 절대 하지 않는 것

- prettier를 전체에 돌리지 않는다 (손댄 파일에만). 한 번 42개 파일을 건드렸다 되돌린 적 있다.
- 배포는 CLI(`npx vercel --prod`)로. **Vercel MCP는 쓰지 않는다** — 배포 1회에 약 24만 토큰.
- 테스트 계정을 만들었으면 **그 세션 안에서 지운다.**
- 토큰·판정 변경은 **사용자 승인 없이 하지 않는다.**

## 테스트 시나리오

**정상 흐름:** "홈 화면 이식하자" → Phase 0에서 `_workspace/` 없음 확인 → Phase 1 토큰
대조 후 승인 → `home` 추출 → 이식 → 검증 2개 병렬 → 지적 3건 수정 → verify.sh 통과 →
스크린샷 제시 → 사용자 확인 → `PROGRESS.md` 갱신 → 다음 화면 제안.

**에러 흐름:** 검증에서 "방 A→B 이동 시 A 데이터가 잠깐 보임(`key` 누락)" BLOCK →
이식가 수정 1회 → 재검증에서 같은 증상 → 수정 2회 → 여전히 실패 → **3회째 시도하지 않고**
"명세의 라우팅 구조 자체를 다시 봐야 한다"고 사용자에게 보고.

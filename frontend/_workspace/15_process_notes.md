## 2026-08-24

### #1. 타깃을 정정하니 결론이 더 단단해졌다

**상황.** 그동안 "사용자는 5060 부모"라는 전제로 판단해왔다.
실제 타깃은 **"후회하고 싶지 않은, 가족과 유대감을 쌓고 싶은 2030 자녀"** 이고,
부모(5060)는 **자녀에게 초대받아 들어오는 쪽**이다.

**왜 중요한가.** 이 서비스는 **초대로만 굴러간다.** 2030이 앱을 발견해서 가입하고,
부모를 초대한다. 즉 **획득(acquisition)은 2030에게 일어나고, 활성화(activation)는
5060에게 일어난다.** 두 집단의 난이도가 다르므로 퍼널도 둘로 나눠 봐야 한다.

**파급.**
- 계측 이벤트에서 **B. 초대 → 구성원 퍼널의 비중을 올렸다.** 여기가 실제 병목이다
- "웹으로 유저 테스트한다"는 판단이 **약해진 게 아니라 강해졌다** (아래 #2)

### #2. 앱이 최종인데 왜 웹으로 테스트하는가

**상황.** "앱이 최종이고 테스터를 많이 모으려면 앱이 낫지 않나?" 라는 질문.
방향이 반대다.

**테스터가 겪는 일:**

| | 절차 |
|---|---|
| 웹 | 카톡 링크 → 누름 → 끝. **3초** |
| iOS 앱 | TestFlight 설치 → Apple 계정 → 초대 메일 수락 → 다운로드 |
| Android 앱 | 내부 테스트 트랙 등록 → 구글 계정 등록 → 설치 |

**결정적인 이유 3가지:**

1. **테스터는 설치 단계에서 증발한다.** 그리고 우리 구조에서 **설치를 해야 하는 쪽은
   초대받는 부모(5060)** 다. 획득은 2030이라 앱 설치가 가능해도, **활성화가 막힌다.**
   초대 퍼널이 핵심인 서비스에서 이건 치명적이다
2. **비용과 시간** — iOS는 Apple Developer $99/년 + 심사 리젝 왕복 며칠
3. **앱이어야만 알 수 있는 게 없다** — 이번에 알고 싶은 건 "몽실이 제스처가 통하는가"
   이고, 그건 웹에서 100% 측정된다

**그럼 앱은?** 버리는 게 아니라 **순서를 뒤로 미룬다.** 경로도 재작성이 아니라
**Capacitor 래핑**이다. 지금 Next.js 웹앱을 그대로 감싸면 되고, 그때 바뀌는 건
**푸시 경로(FCM/APNs)와 햅틱, 둘뿐**이다. **DB(Supabase)는 그대로다.**

> "FCM 추가"는 **배달부를 바꾸는 것**이지 창고를 옮기는 게 아니다.
> 웹푸시는 브라우저가 VAPID로 직접 받고, 앱은 브라우저가 없어서 OS 푸시를 거쳐야 한다.

**포폴 관점:** "웹으로 검증하고 앱으로 확장했다"가 "처음부터 앱으로 만들었다"보다
설명할 게 많은 서사다. 앱화 자체가 한 챕터가 된다.

### #3. 보호자 문자 인증 — 로그인 전 기능의 보안 함정

**상황.** 만 14세 미만 가입 시 보호자 번호로 동의 문자를 보내고 인증번호를 확인해야 한다.
그런데 이 기능은 **가입 전, 즉 로그인이 안 된 익명 상태에서 돈다.**

**함정.** 익명이 호출할 수 있는 것은 **공격자도 그대로 호출할 수 있다.**
Supabase는 DB가 REST로 직접 열려 있어서, "우리 앱 화면에서만 부른다"는 보장이 없다.

만약 이렇게 설계했다면:

```
앱 서버가 인증번호를 만든다 → DB에 해시를 넘긴다 → 문자를 보낸다
```

공격자는 **자기가 아는 번호의 해시를 직접 DB에 넣고, 문자를 받지도 않고
바로 그 번호로 인증을 통과시킬 수 있다.** 자가 인증이다. 절차가 통째로 무의미해진다.

**원칙.** 인증번호는
1. **신뢰된 곳에서만 만들어지고**
2. **호출자에게 절대 돌려주지 않는다**

**선택지 3개:**

| | 방식 | 판정 |
|---|---|---|
| A | Next.js 서버액션 + `service_role` 키 | ❌ PRD가 금지 (`push.ts:12`). 만능 키를 앱 코드에 두면 실수 한 번에 전부 뚫린다 |
| B | **Supabase Edge Function** | ✅ 채택 |
| C | Postgres 안에서 `pg_net` 으로 직접 SMS 발송 | ❌ API 키 관리와 HMAC 서명이 plpgsql로 들어가 복잡해진다 |

**B를 고른 이유.** Edge Function은 Supabase가 운영하는 별도 실행 공간이라
`service_role` 권한과 SMS API 키를 **앱 코드 바깥에** 둘 수 있다.
PRD의 금지 취지("만능 키를 Next.js 앱에 두지 않는다")를 지키면서 필요한 권한을 얻는다.

**그래서 나온 구조:**

```
[브라우저]  --인증번호 요청-->  [Edge Function]  --문자-->  [보호자 휴대폰]
                                  (service_role)
                                       |
                                  코드 해시만 저장
                                       v
                              guardian_verifications
                                       ^
                                       | "이 인증 완료됐어?" 만 물어봄
[가입 서버액션] --consume_guardian_verification()--+
   (익명 키)        security definer 함수
```

**권한 설계의 핵심 두 줄:**

```sql
alter table public.guardian_verifications enable row level security;
-- 정책을 하나도 만들지 않는다 = service_role 외에는 아무도 직접 못 읽고 못 쓴다
```

RLS를 켜고 **정책을 비워두는 것**이 "아무나 접근 금지"의 표현이다.
이건 실수가 아니라 의도이므로, 마이그레이션에 주석으로 남겼다.

그리고 가입 서버액션(익명 키)은 테이블을 직접 못 읽으므로,
**딱 하나의 질문만 하는 창구**를 열어줬다:

```sql
consume_guardian_verification(p_id uuid, p_phone text) returns boolean
```

이 함수가 익명에게 열려 있어도 안전한 이유: **`verified_at` 은 올바른 인증번호를
넣었을 때만 Edge Function 쪽에서 찍힌다.** id 를 안다고 통과시킬 수 없다.
그리고 `consumed_at` 을 찍어 **한 번 쓴 인증은 재사용할 수 없게** 했다.

**추가로 넣은 방어:**
- `expires_at` — 발송 후 5분
- `attempts` — 인증번호 무차별 대입 차단
- `guardian_phone` 형식 체크 (`^01[0-9]{8,9}$`)
- 번호+시각 인덱스 — **같은 번호로 문자 폭탄을 못 보내게** 최근 발송 횟수를 세는 용도
- 평문 인증번호는 **저장하지 않는다** (해시만)

**남은 숙제.** 가입을 끝내지 않고 버려진 행에도 보호자 번호가 남는다.
개인정보 최소보관 원칙상 **24시간 지난 행은 지워야 한다.** 테이블 주석에 적어뒀고,
정리 작업은 SMS 연동을 붙일 때 함께 넣는다.

### #4. NOT NULL 을 풀면서 보장은 잃지 않는 법

**상황.** `push_subscriptions` 가 웹푸시 전용 모양이었다.

```
endpoint, p256dh, auth   ← 전부 Web Push(VAPID) 규격 필드, 전부 NOT NULL
```

앱을 붙이면 FCM/APNs **토큰**이 오는데, 이 모양에는 안 들어간다.
나중에 반드시 고쳐야 할 자리다. **지금 열어두면 마이그레이션 없이 꽂힌다.**

**여기서 조심할 것.** 컬럼을 추가하면서 `endpoint` 등의 NOT NULL 을 풀어야 하는데,
**그냥 풀면 "웹인데 endpoint 가 없는 행"이 만들어질 수 있다.** 제약을 푸는 건
언제나 보장을 잃는 일이다. (실제로 2026-08-24 오전에 작업자가 `birth_date` 의
NOT NULL 을 임의로 풀어 법적 요건이 무너진 사고가 있었다. → `CLAUDE.md` 맨 위 규칙)

**그래서 푼 만큼 다시 채웠다:**

```sql
check (
  (platform = 'web'
     and endpoint is not null and p256dh is not null and auth is not null)
  or
  (platform in ('ios','android') and token is not null)
)
```

컬럼 단위 NOT NULL 을 **행 단위 조건부 제약으로 옮긴 것**이다.
"웹이면 웹푸시 3종이 반드시 있고, 앱이면 토큰이 반드시 있다"가 DB에서 계속 보장된다.

**교훈.** 제약을 풀어야 할 때는 *"풀어도 되나?"* 가 아니라
***"푼 보장을 어디서 다시 지킬 것인가?"*** 를 묻는다. 답이 없으면 풀면 안 된다.

**적용 결과 (검증 완료):**
```
push_subscriptions: id(NN) user_id(NN) endpoint(null) p256dh(null) auth(null)
                    created_at(NN) platform(NN) token(null)
guardian_verifications RLS 정책 수: 0   ← 의도된 값
consume_guardian_verification 실행 권한: anon, authenticated
```

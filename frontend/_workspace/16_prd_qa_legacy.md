## 원문

실습 프롬프트3 - PRD 개선
1. 개발자가 코드 짜다가 되물어볼 모호한 표현
[ALBUM-01] 앨범방 생성
PRD 내용: "동일 이름 생성 시 허용하되 구분용 생성일 표시"
QA의 태클: 구분용 생성일을 어디에, 어떤 포맷으로 표시하라는 건가요?
홈 화면 카드 타이틀 옆에 (2026-07-10) 처럼 붙이는 건지, 아니면 카드 하단에 작게 타임스탬프를 찍는 건지 명확하지 않습니다.
데이터베이스 단에서 DB 유니크 키(Unique Key)를 방 이름이 아닌 별도의 room_id로 파야 한다는 힌트는 되지만, UI/UX 관점의 출력이 흐릿합니다.
[MISSION-01] 답장 미션 및 열람 제한
PRD 내용: "동일 발신자의 메시지를 5개까지 읽으면 답장 미션이 활성화된다."
QA의 태클: 이 '5개'의 기준이 누적인가요, 아니면 미답장 상태로 연속된 개수인가요?
만약 누적이라면, 사용자가 서비스 가입 후 평생 동안 상대방에게 5번 메시지를 읽고 답장을 다 했어도 6번째 메시지부터 영원히 락이 걸린다는 뜻이 됩니다.
개발자는 is_read뿐만 아니라 has_replied 상태 값이나 unread_message_count 같은 카운팅 로직을 설계해야 하므로, 이 조건은 "답장을 하지 않은 채 쌓인 상대방의 미확인/미답장 메시지가 연속 5개일 때" 처럼 물리적으로 정의되어야 합니다.
2. 누락된 예외 처리 및 기획적 구멍 (Edge Case)
💣 초대 링크/QR과 회원가입 흐름의 모순 ([INVITE-01], [INVITE-02])
상황: "초대 메시지 작성 후에만 링크가 생성" 되며, 초대받은 사람은 "가입 후 반드시 초대 메시지에 대한 답장을 작성해야 방에 진입" 합니다.
엣지 케이스: 만약 '엄마'를 초대하기 위해 링크를 생성해서 카톡으로 보냈는데, 엄마가 스마트폰 조작 실수로 링크를 누르고 가입 폼까지만 진행한 뒤 앱을 강제 종료했다면 어떻게 되나요?
다시 카톡 링크를 누르고 들어왔을 때, 기획상 가입은 이미 되어 있으니 준회원 상태일 텐데, 이때도 초대 메시지가 선재생되고 답장 폼이 정상 작동하나요?
만약 이 링크를 엄마가 아닌 '아빠'가 잘못 눌러서 가입했다면, 시스템은 아빠를 '엄마' 권한으로 방에 매핑하게 되나요? (초대 생성 시 이미 관계를 '엄마'로 지정했으므로)
💣 미디어 업로드 실패 및 비동기 업로드 정책 ([ALBUM-02])
상황: 사진/영상을 업로드하면 피드에 등록되고 구성원에게 알림이 갑니다.
엣지 케이스: 시니어 가구 특성상 와이파이가 불안정한 환경이 많습니다. 3초짜리 고용량 영상을 업로드하다가 80% 시점에서 네트워크가 끊기거나 백그라운드로 전환되면 어떻게 처리하나요?
UI에 '업로드 중...'인 프로그레스 바를 계속 띄워둘 것인지, 실패 시 로컬(Local DB)에 임시 저장을 해두고 재연결 시 자동 재시도(Retry) 알고리즘을 돌릴 것인지 백엔드/클라이언트 간 싱크 정책이 전무합니다.
💣 삭제된 원본의 '감정 사서함' 보존 법칙 ([BOX-01])
상황: "원본 사진/영상이 삭제되어도 사서함 내 메시지 데이터는 유지" 한다고 했습니다.
엣지 케이스: 앨범 피드에서 원본 사진이 삭제되었습니다. 사서함에서 그 메시지를 클릭하면 "원본 게시물이 삭제된 마음입니다"라고 뜹니다.
그런데 그 메시지가 [MISSION-01]의 답장 미션 카운트(5개)에 포함되어 있던 메시지라면? 원본이 삭제되었으니 사용자는 그 메시지에 답장을 남길 수 없게 되나요? 답장을 못 남기면 다음 메시지 열람 락(Lock)은 영원히 안 풀리나요? 미션 카운트에서 삭제된 원본의 메시지는 제외해 주는 로직이 누락되었습니다.
3. 개발자를 춤추게 할 구체적인 수정 제안 (PRD 보완 리팩토링)
PRD 스펙을 명확한 개발 스펙으로 전환하기 위해 아래와 같이 조항을 수정 및 추가해 주세요.
수정안 1: [MISSION-01] 미션 활성화 조건 논리 정립
기존: 동일 발신자의 메시지를 5개까지 읽으면 미션 활성화
변경: "특정 발신자가 보낸 메시지 중, '수신자가 읽었으나 답장을 하지 않은 메시지'가 누적 5개가 되는 시점에 락(Lock) 스케줄러가 발동한다. 6번째 메시지 데이터는 서버에서 클라이언트로 보낼 때 본문(Body)을 블러(Blur) 처리하고 마스킹된 상태(is_locked: true)로 내려주며, 답장 API가 성공 수신(200 OK)되어야만 해당 발신자의 락 카운트가 0으로 초기화되고 메시지가 복호화된다."
수정안 2: [INVITE-02] 초대 검증 및 예외 스펙 추가
추가할 예외 처리:
[예외 3] 준회원 상태에서 이탈 후 재진입 시: 가입 세션은 유지하되, has_replied_first_invite: false인 경우 홈 화면 진입을 차단하고 웰컴 페이지(초대 메시지 재생 및 최초 1회 답장 필수 폼)로 강제 리다이렉트(Redirect)한다.
[예외 4] 관계 설정 미스매치 방지: 초대 링크 생성 시 고유 토큰(invite_token)을 발행하며, 가입 단계에서 유저가 자신의 최종 프로필 관계명(예: 엄마 -> 아빠)을 수동으로 수정할 수 있는 방어 UI를 한 단계 제공한다.
수정안 3: [BOX-01] 원본 삭제 시 미션 예외 정책 추가
추가할 기능 정책:
[제한정책] 앨범방 피드에서 사진/영상이 삭제될 경우, 사서함 내 텍스트/음성 메시지는 보존되나 [MISSION-01]의 미션 제한 카운팅 대상에서는 즉시 제외 처리한다. 만약 6번째 잠겨있던 메시지의 원본이 삭제된 경우, 해당 락은 무조건 자동 해제(is_locked: false)된다.

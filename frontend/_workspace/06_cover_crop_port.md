## 1. 무엇이 달라졌나

| | 이전 | 지금 |

### 참고 이미지에서 가져온 것

- 사진 전체 위에 얹힌 **자르는 틀**, 틀 밖 어둡게 덮기

- **재설정** 버튼 (틀·배율·위치를 처음 상태로)

### 안 가져온 것과 이유

| 참고 이미지의 것 | 왜 뺐나 |
|---|---|
| 조절 / 필터 탭 | **이번 요청 범위 밖.** 밝기·색감 보정은 "사진 크기 조절" 과제가 아니다. 넣으면 원본 픽셀을 바꾸는 기능이 되고, 되돌리기·미리보기 등 딸린 것이 한 무더기 늘어난다. |

| 자유 비율 자르기 | 커버는 홈 카드와 같은 **2:1 고정**이어야 한다(`COVER_ASPECT`). 어느 손잡이를 끌어도 2:1을 지키며 커지고 작아진다. |
| "완료"라는 문구 | **"선택"을 유지했다.** 이 창은 사진 편집이 끝나는 곳이 아니라 앨범방 만들기 폼에 커버를 **고르는** 한 단계다. 창을 닫아도 방은 아직 안 만들어졌는데 "완료"라고 하면 다 끝난 줄 안다. 캡처 07의 원래 문구이기도 하다. |
| 빨간 "복귀" 버튼 | 사진 앱에는 이미 저장된 편집을 되돌리는 뜻이 있다. 우리는 매번 원본에서 새로 시작하므로 **재설정 하나면 충분**하다. |

## 2. 계산 로직 — 무엇을 다시 썼나

### 좌표계

무대(사진이 놓이는 칸) 왼쪽 위를 원점으로 잡는다. 모든 값이 이 하나의 좌표계에 있다.

```
fitScale  = 사진 한 장이 무대에 통째로 들어오는 배율   (이전의 baseScale = "꽉 채우는" 배율과 반대)
scale     = fitScale × zoom
imageRect = 무대 안에서 사진이 차지하는 사각형
crop      = { x, y, w }  — 자르는 틀. 높이는 언제나 w / 2 라 담지 않는다
```

### 지켜야 하는 단 하나의 약속

> **틀 ⊆ (사진 ∩ 무대)**

틀이 사진 밖으로 나가면 결과에 빈칸이 찍히고, 무대 밖으로 나가면 사용자가 못 본다.
두 조건을 `getAllowedBox()` 로 **상자 하나**로 합쳐 두어서, 이후 계산은 전부 "이 상자 안에서"로 끝난다.

약속을 어디서 지키는지 **한 방향으로만** 정했다(서로가 서로를 고치면 순환한다):

| 사용자가 한 일 | 고정 | 가두는 것 |
|---|---|---|
| 손잡이 끌기 | 사진 | `clampCrop` — 틀을 상자 안으로 |
| 사진 끌기 | 틀 | `clampOffset` — 사진이 틀을 덮도록 이동량을 |
| 휠·핀치 | 틀 | `getMinZoom` 으로 배율 하한을 만들고, 이동량을 다시 가둠 |

`crop` 이 기준이고 `offset`·`zoom` 이 거기 맞춘다. 반대는 없다.

### 손잡이 하나가 가로·세로를 동시에 정한다 (`resizeCrop`)

2:1 고정이라 "가로 하나"만 정하면 나머지가 따라온다.

1. 잡은 손잡이의 **맞은편 변(모서리)은 고정**한다. (se를 끌면 nw가 안 움직인다)
2. 손이 간 거리에서 가로 후보를 뽑는다. 모서리는 가로·세로 두 후보 중 **큰 쪽**을 따른다 —
   대각선으로 끌 때 손을 따라오는 느낌이 난다.
3. 변 손잡이는 반대 축을 **가운데 기준으로** 늘린다(위 변을 끌면 좌우가 같이 벌어진다).
4. 상자가 허용하는 최대 가로를 계산해 자른다.

### 결과 굽기 (`handleConfirm`)

출력은 그대로 **1200×600 JPEG**. source 좌표만 다시 썼다.

```
이전:  칸 가운데를 기준으로 offset 을 되돌려 계산
지금:  sourceX = (crop.x - imageRect.x) / scale      ← 틀의 왼쪽 위가 사진의 어디인가
       sourceW = crop.w / scale
```

무대 좌표의 틀에서 사진 왼쪽 위 위치를 빼고 배율로 나누면 곧바로 원본 좌표다.
반올림 오차로 원본 밖을 가리키지 않도록 마지막에 한 번 더 가둔다.

## 3. 그대로 지킨 것

- **`FileReader`** (StrictMode 이중 마운트에서 `URL.createObjectURL` 이 죽은 주소를 남기는 문제) — 손대지 않음
- **`<dialog>` + `showModal`** (초점 가두기·Esc) — 손대지 않음
- **1200×600 JPEG 굽기** — 손대지 않음
- **키보드 조작** — 화살표로 사진 옮기기는 그대로 두고, **`+` / `−` 로 틀 크기**를 추가했다.
  aria-label 도 그에 맞게 고쳤다: "커버 자르기 (화살표 키로 사진 옮기기, + − 키로 틀 크기 조절)"
- **색 토큰** — 글자·버튼은 전부 globals.css 토큰. 격자선·손잡이의 흰색과 덮개의 반투명 검정만
  예외인데, 크롭 UI의 관례색이고 참고 이미지도 같다. hex 가 아니라 `bg-white/40`·`rgba(0,0,0,0.5)` 라
  잔여데이터 검사기의 `hardcoded-color` 규칙(토큰에 없는 hex)에도 걸리지 않는다.

| 잡는 자리 크기 | 보이는 표시(20px 갈고리)보다 넓은 **36px** | 표시에 딱 맞추면 손가락으로는 거의 안 잡힌다. |

| 화면 크기 변화 | 무대 가로가 바뀌면 틀·이동량을 **같은 비율로** 늘리거나 줄임 | 안 그러면 화면을 돌렸을 때 틀만 제자리에 남아 엉뚱한 곳을 가리킨다. |

# 7. 전체화면으로 (2026-08-10, 같은 날 2차 지시)

> 사용자가 실제 화면을 보고: **"너무 작아서 안 보여. 참고 사진은 화면에 꽉 차서 조절하기도 쉬웠잖아."**

맞는 지적이었다. 조작 방식만 바꾸고 **껍데기는 예전 슬라이더 시절 그대로** 뒀던 것이 원인이다.
`w-[min(92vw,26rem)]` 짜리 작은 카드 안에 제목·설명·틀·버튼을 다 욱여넣으니,
손끝으로 손잡이를 잡아 끄는 도구인데 정작 틀이 손톱만 했다.

## 무엇을 바꿨나 — 레이아웃만

계산 로직(2장)은 **한 줄도 건드리지 않았다.** 무대 크기는 `ResizeObserver` 가 재므로
껍데기가 커지면 틀도 저절로 따라 커진다. 바꾼 것은 배치뿐이다.

```
이전                              지금
┌─ 작은 카드(≤26rem) ─┐          ┌─ 화면 전체 ────────────┐
│ 제목                │          │ 취소   커버사진 선택  재설정 │  ← 위 도구줄
│ 설명 두 줄          │          │ 안내 한 줄                │
│ ┌ 무대 4:3 ┐        │          │ ┌──────────────────┐ │
│ │  틀      │        │          │ │                  │ │
│ └──────────┘        │          │ │   무대 = 남는 자리 전부  │ │
│ [재설정][취소][선택] │          │ │       틀           │ │
└─────────────────────┘          │ └──────────────────┘ │
                                  │ [        선택        ] │  ← 아래 고정
                                  └────────────────────────┘
```

- `<dialog>` 의 기본 여백·최대크기를 전부 풀었다: `m-0 h-dvh max-h-none w-screen max-w-none`.
  `dvh` 를 쓴 이유는 모바일 주소창이 접혔다 펴져도 높이가 어긋나지 않기 때문이다.
- 무대는 비율을 박지 않고 **`flex-1` 로 남는 자리를 통째로** 쓴다. `min-h-0` 을 같이 준 이유:
  flex 자식은 기본이 "내용보다 작아지지 않음"이라 이걸 풀어야 남는 자리에 맞춰진다.
- 위 도구줄 = 취소 · 제목 · 재설정, 아래 = 선택. **참고 이미지의 자리 배치 그대로**다.

## 판단 기록

| 갈림길 | 정한 것 | 근거 |
|---|---|---|
| 제목·설명을 아이콘 도구줄로 압축할까 | **제목은 한 줄로 줄이고, 안내 문구는 남겼다** | 아이콘만으로는 무엇을 하는 화면인지 알기 어렵다. 처음 쓰는 시니어 사용자에게 이 한 줄이 화면 전체의 설명이다. 대신 두 줄이던 것을 한 줄로 줄여 무대에 자리를 넘겼다. |
| 위 도구줄 버튼에 `Button` 부품 | **안 썼다. 흰 글자 버튼을 직접 만들었다** | primary(#d50e68)도 secondary(흰 바탕)도 **검정 위에 놓으라고 만든 색이 아니다** — 검정 위 primary는 대비가 모자란다. 흰 글자로 대비를 최대로 하고, 부품이 지키던 것(글자 17px·터치 목표 44px)은 그대로 지켰다. |
| 확정 버튼 | **`Button` 기본 크기(lg, 52px) 그대로** | 되돌릴 수 없는 확정 동작은 예외 없이 lg — 프로젝트 규칙이다. 화면 아래에 고정하고 `env(safe-area-inset-bottom)` 으로 홈 인디케이터를 피한다. |
| 오류 문구 | `text-primary` → **primary 바탕 + 흰 글자** | 검정 위에서는 글자색만 바꿔서는 안 보인다. 이 조합은 primary 버튼과 같아서 새로 정한 색이 아니다. |
| 무대 좌우 여백 | **없음(꽉 채움)** | 여백을 주면 다시 작아진다. 틀이 최대 크기일 때 모서리 손잡이의 잡는 자리(36px)가 절반쯤 화면 밖으로 나가지만, 그 상태에서 할 수 있는 일은 "줄이기"뿐이라 안쪽 절반만으로 충분하다. |

# 8. 손잡이 터치 영역 44px (2026-08-10, 통합 검증 지적)

> 검증가 실측: 크롭 손잡이 8개의 잡는 자리가 **36px**(실측 38px).
> 이 프로젝트 기준은 **44px 이상**(시니어 사용자 대상)이다.

## 무엇을 바꿨나

`h-9 w-9`(36px) → **`h-11 w-11`(44px)**. 한 줄이다.

**보이는 모양은 그대로 뒀다** — 모서리 갈고리 20px, 변 막대 28px×3px.
참고 이미지의 가는 선 느낌을 잃지 않으면서 손가락이 닿는 넓이만 키우는 방법이,
보이지 않는 44×44 정사각형을 표시 위에 겹치는 것이다. 처음부터 표시와 잡는 자리를
따로 만들어 둔 덕에 값 하나만 바뀌었다.

## 같이 고친 것 — 손잡이 겹침 순서

44px로 키우면 **틀이 작을 때 변과 모서리의 잡는 자리가 겹친다.**
(틀 최소 가로는 `MIN_CROP_WIDTH` = 72px, 그때 높이는 36px이므로 세로로는 반드시 겹친다.)

겹친 자리는 **나중에 그려진 쪽이 이긴다.** 그래서 `HANDLES` 배열 순서를
`변 4개 → 모서리 4개`로 바꿔 **모서리가 이기게** 했다. 모서리는 가로·세로를 한 번에
정하는 손잡이라 틀이 작을 때 더 자주 쓴다. 변 손잡이만 못 잡게 되는 상황은 있어도,
모서리로 할 수 있는 일이 변으로 할 수 있는 일을 포함한다.

기본 크기(500×250)에서는 손잡이 사이가 가로 250px·세로 125px이라 **겹치지 않는다.**

## 실측 확인 (2026-08-10)

브라우저 MCP가 다른 작업자와 공유되다가 중간에 끊겨(`browser is already running`) 쓸 수 없었다.
대신 **내 전용 헤드리스 Chrome을 따로 띄워** CDP로 요소 크기를 직접 쟀다.
빌드 산출물의 실제 CSS를 그대로 넣고, 손잡이 마크업은 컴포넌트의 클래스 문자열을 그대로 옮겼다.

```
손잡이 8개 전부 — 46.75 × 46.75 px      (기준 44px 이상 ✓)
기본 틀 크기(500×250)에서 모서리·변 손잡이 겹침 — 없음 ✓
```

**왜 44가 아니라 46.75인가** — 검증가가 "36px 클래스인데 38px"이라 한 것과 같은 이유다.
`globals.css`가 뿌리 글자 크기를 **17px**로 잡는다(시니어 가독성). Tailwind의 `--spacing`은
rem 기준이라 모든 간격이 17/16 = 1.0625배가 된다.

```
36px 클래스 → 38.25px 실측   (검증가가 잰 38px)
44px 클래스 → 46.75px 실측   (지금)
```

즉 기준 44px을 넉넉히 넘긴다. 클래스 이름만 보고 추정한 것이 아니라 브라우저가 그린 상자를 쟀다.

## 손대지 않은 것

`RoomCard.tsx`의 커버 비율(`h-[158px]` → `aspect-[2/1]`)은 조정자가 직접 처리했다고 해서
건드리지 않았다. `COVER_ASPECT = 2`는 그대로 맞다 — 이제 카드가 어느 화면 폭에서도
2:1이므로 "밝은 틀 안이 커버가 돼요"라는 문구가 실제와 정확히 맞는다.

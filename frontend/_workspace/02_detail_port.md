> 기준: `_workspace/03_capture_flow.md` (캡처 10, 12~23)

## 한 줄 요약

앨범방 상세를 **1:1 마음 목록에서 추억 피드로** 갈아끼우고, 작성 화면을
**사진 1~10장 + 목소리 + 문구**를 담는 캡처 그대로의 화면으로 다시 짰다.
`heart_messages`(사서함용)는 한 줄도 건드리지 않았다 — 이 화면에서 안 보일 뿐이다.

## 1. DB 변경 (마이그레이션 2건)

### `memories_voice_and_caption`

| 항목 | 내용 |
|---|---|
| `media_url` | NOT NULL 해제 + `(폐지)` 주석. 사진은 `memory_photos`로 옮겼다 |
| `media_type` | `default 'photo'` 추가 (신고 화면이 명사 "사진"을 고를 때만 쓴다) |
| `voice_path` | 신규. `voice` 버킷 경로 `{room_id}/파일명` |
| `voice_duration_sec` | 신규. 3~60초 |
| CHECK `memories_voice_pair` | 경로와 길이는 **항상 함께 있거나 함께 없다** |
| CHECK `memories_description_length` | 문구 300자 (`heart_messages.text_length_limit`과 같은 값) |
| INDEX `memories_room_created_idx` | `(room_id, created_at desc)` — 피드는 늘 이 순서로 읽는다 |

**컬럼을 지우지 않았다.** 물리 삭제 금지 원칙이고, 1단계의 `relationship_type`과 같은 방식이다.

### `memory_photos` (신규 테이블)

```
id / memory_id(fk, on delete cascade) / storage_path / sort_order(0~9) / created_at
unique(memory_id, sort_order),  index(memory_id, sort_order)
```

`sort_order = 0`이 **대표 사진**이다. 순서를 컬럼으로 못 박은 이유:
피드에서 "왼쪽 큰 사진"이 늘 대표 사진이어야 하는데, 순서가 없으면 조회할 때마다 바뀐다.

RLS는 부모 게시물의 조건을 **그대로 다시 적었다**(`is_room_member` + `not has_blocked`).
부모 테이블 RLS에 기대어 조건을 생략하면 나중에 `memories` 정책이 바뀔 때 사진만 조용히 샌다.

### 스토리지 — 새 정책 없음

`media_voice_insert/select/delete` 정책이 이미 `media`·`voice`·`covers` 세 버킷을
`is_room_member(path_uuid(name))`로 함께 덮고 있었다. 커밋 `c79f27b`이 겪은
"PERMISSIVE끼리 OR로 합쳐지는 함정"을 피하려고 **정책을 새로 만들지 않고 그대로 얹었다.**

- **피드 화면은 서버 컴포넌트**다. DB 조회·서명 주소 만들기·정렬을 전부 서버가 하고

## 3. 캡처와 다르게 한 것과 이유

**① 검색·햄버거(더보기 드로어)를 넣지 않았다** — 지시대로.
5단계 몫이라 지금 넣으면 눌러도 아무 일이 없는 버튼이 된다.

**② 대신 머리띠에 [방 설정]을 뒀다 (캡처에 없는 버튼).**
캡처는 '앨범방 나가기'를 햄버거 드로어 안에 둔다. 그 드로어를 만들기 전에 이 버튼을 빼면
**방 나가기·멤버 차단으로 갈 길이 아예 없어진다**(기존에 있던 입구다). 5단계에 이 자리를 넘긴다.
아이콘은 톱니 대신 **조절 손잡이 모양**을 썼다 — 22px 톱니가 실제 화면에서 밝기(해) 아이콘처럼 읽혔다.

**③ 게시물 오른쪽 위 ⋯(고정·수정·숨기기·저장·삭제)를 넣지 않았다** (캡처 22·23).
게시물 관리는 다음 단계다. ②와 같은 이유로 껍데기를 두지 않았다.

**④ ♡·💬는 버튼이 아니라 글이다.** 지시대로 수만 0으로 보여준다.
버튼처럼 생겼는데 눌리지 않으면 "내가 잘못 눌렀나" 하고 멈칫한다. 3단계에 이 자리가 버튼이 된다.

**⑤ "✓ 3초 이상 충족 완료" 배지가 초록이 아니다.**
캡처는 초록인데 `globals.css`에 초록 토큰이 없다. **색을 즉흥으로 만들지 않는다**는 원칙이 우선이라
"아직"은 강조색(분홍), "됐다"는 가라앉은 면으로 뒀다. 상태는 **✕/✓ 기호가 함께 바뀌어** 전달된다(WCAG 1.4.1).
초록이 꼭 필요하면 성공 토큰을 디자인 관문에서 정식으로 추가해야 한다 — 이번 범위 밖이다.

**⑥ 녹음 중에는 파형을 그리지 않는다.** 캡처 16이 카운터만 보여준다.
소리 크기는 녹음하는 내내 재고 있지만, 화면에 막대를 띄우면 녹음 중에 카드 높이가 바뀐다.
재어 둔 값은 정지 직후 재생바(캡처 18)에 그대로 쓰인다.

**⑦ 머리띠를 `layout.tsx`에서 화면별로 옮겼다.**
화면마다 제목도 오른쪽 동작도 다르고(피드=방 이름+멤버추가, 작성="마음 표현하기"),
피드는 머리띠·본문·고정버튼·탭까지 4단 셸이라 공통 껍데기 안에 넣으면 자리를 못 잡는다.
레이아웃은 "이 방의 멤버인가"만 확인한다. 덤으로 레이아웃에 남아 있던
**관계유형 부제(`relationshipTypeLabel`)가 사라졌다** — 캡처 기준으로는 없어야 하는 것이다.

**⑧ 뒤로 버튼이 꺾쇠 하나다** (기존 `BackLink`는 "뒤로" 글자를 달고 있었다).
캡처 그대로다. 이 앱은 아이콘만 두지 않는 것이 원칙이지만(BottomNav) 여기는 **바로 옆에 제목이 붙어**
어디서 뒤로 가는지가 글자로 드러나고, 낭독기에는 목적지를 이름으로 전한다(`홈으로 돌아가기` 등).
`BackLink.tsx`는 부르는 곳이 0곳이 됐지만 지우지 않았다.

## 4. 판단이 갈렸던 지점

**(1) 사진을 `media_url`에 대표 사진으로 중복 저장할까?**
안 했다. `media_url`을 대표 사진 경로로 쓰면 `memory_photos[0]`과 **같은 사실을 두 곳에 적는 것**이고,
언젠가 어긋난다. 대신 컬럼을 폐지하고 대표 사진은 `sort_order = 0` 하나로만 정한다.

**(2) 사진을 언제 올리나 — 고를 때 vs 표현할 때.**
표현할 때다. 고를 때 올리면 ×로 뺀 사진이 스토리지에 고아로 남는다.
고르는 순간에는 브라우저에서 **크기만 줄여서**(긴 변 1600px JPEG 0.85) 쥐고 있는다.
서버 액션 본문 1MB 제한은 애초에 지나갈 일이 없다 — 액션은 **경로만** 받는다.

**(3) 사진 저장 중간에 실패하면?**
방금 만든 `memories` 줄을 되돌린다. 안 그러면 사진 없는 카드가 피드에 영영 남는다.
이건 "남의 기록 삭제"가 아니라 **완성되지 못한 내 요청 취소**라 물리 삭제 금지에 걸리지 않는다.
`residue-scan-allow: physical-delete` 사유를 코드에 적어 뒀다.

**(4) 파형 막대 높이 — 이게 이번에 가장 크게 고친 부분이다.**
처음에는 **막대를 전부 55% 높이로** 그려놓고 누르면 그때 파일을 해석하게 했다.
사용자가 바로 잡아냈다 — **파형처럼 보이지만 소리와 아무 상관이 없는 그림**이었다. 고쳤다:

| 어디 | 높이의 출처 |
|---|---|
| 녹음 직후 미리듣기 | 녹음하는 **내내 `AnalyserNode`로 잰 실제 크기**(RMS). 파일을 다시 해석하지 않는다 |
| 피드의 저장된 음성 | 화면에 뜰 때 파일을 내려받아 해석(`decodeAudioData`). **누르기 전에도 실제 파형이다** |
| 아직 모를 때 | 막대를 그리지 않고 **납작한 줄 하나**. 지어낸 모양을 그리느니 "모른다"를 그대로 보인다 |

두 길이 만나는 지점(`toBarLevels`)을 `src/lib/waveform.ts` 한 곳에 뒀다 —
같은 소리가 화면마다 다른 모양이면 안 된다. `VoicePlayer`는 `levels` prop을 받으므로
사서함(4단계)에서도 재어 둔 값을 그대로 넘겨 쓸 수 있다.

**(5) 사진 그리드가 카드를 뚫고 나갔다 (브라우저에서 잡음).**
세로로 긴 사진 한 장이 `aspect-[4/3]`을 무시하고 카드를 화면 밖까지 밀어냈다.
원인은 **격자 칸의 기본값 `min-height: auto`** — 칸이 사진의 원래 높이만큼 늘어난다.
칸에 `min-h-0`을 주는 것으로 고쳤다.

## 6-1. 검증 지적 반영 (2026-08-10, `05_stage2_qa.md` "막아야 할 것" 5건)

검증가가 게시물을 여러 개 만들어 돌려보고 찾은 것들이다. §5의 브라우저 확인이
**게시물 1개**로만 이뤄져서 못 봤던 자리다 — 2개부터 보이고 6개부터 깨진다.

### ① 음성 게시물마다 AudioContext를 새로 만들었다

두 겹으로 잘못돼 있었다.

| 무엇 | 전 | 후 |
|---|---|---|
| AudioContext | 카드마다 새로 만들고 닫음 → 7번째부터 예외(크롬 문서당 6개 상한) | **모듈에 하나만** 두고 재사용 (`getDecodeContext`) |
| 생성자 예외 | `try` **바깥**이라 `catch`가 못 잡음 → 미처리 프라미스 거부 | try 안으로. `levelsFromUrl`은 어떤 경우에도 reject하지 않는다 |
| 부르는 쪽 | `void (async () => …)()` 에 try/catch 없음 | `startDecoding`이 한 번 더 잡는다 |
| 언제 해석하나 | **화면에 뜨자마자** → 게시물 30개면 음성 30개를 통째로 내려받음 | **재생을 누른 순간에만.** `preload="none"`이 다시 뜻을 갖는다 |

`audio.play()`의 거절(자동재생 정책)도 잡는다 — 여기도 콘솔로 새던 자리다.

**바뀐 약속:** §4-(4) 표의 "피드의 저장된 음성 — 누르기 전에도 실제 파형이다"는
**더 이상 사실이 아니다.** 누르기 전에는 납작한 줄이고, 누르면 실제 파형으로 바뀐다.
안 들어볼 음성까지 미리 받아두는 값으로는 파일 전체 다운로드가 너무 비싸다.
"모르는 동안 지어낸 모양을 그리지 않는다"는 원칙 자체는 그대로다.

**②의 "서명 요청은 버킷당 한 번"(§2)도 고쳐 읽어야 한다** — 서명은 2회가 맞지만
실제 다운로드는 게시물 수만큼이었다. 이제 진짜로 "누른 것만" 내려받는다.

### ② 사진이 정확히 2장이면 오른쪽 아래가 빈 회색 칸으로 남았다

오른쪽 열이 늘 `grid-rows-2`인데 `rest`에 사진이 1장뿐이라 둘째 행이 비었다.
`hiddenPhotoCount`도 0이라 `+N` 배지조차 안 붙어 그냥 빈 칸이었다.
→ `rest.length === 1`이면 `grid-rows-1`. 1장·3장 이상은 원래대로다.

### ③ 사진 주소를 못 만들면 사진 자리가 통째로 사라졌다

`PhotoGrid`가 `return null`이라 **사용자는 원래 사진 없는 글로 읽었다.**
음성에는 있던 갈래가 사진에는 없었다.
→ `hasPhotos` prop을 받아 "DB에는 있는데 주소를 못 만든" 경우를 구분하고
"사진을 불러오지 못했어요. 잠시 후 다시 열어주세요."를 띄운다(음성 문구와 같은 결).
`page.tsx:64`의 주석이 없는 동작을 있다고 적고 있었다 — 코드와 맞췄다.

**덤도 함께 고쳤다.** `hiddenPhotoCount`를 DB 원본 수로 세던 것을 **서명에 성공한
수**로 바꿨다. 10장 중 4장만 서명되면 "+7"이라 적고 실제로는 1장만 더 있었다.

### ④ 표현하기가 실패한 뒤 나가면 올라간 파일이 영영 남았다

파일은 `createMemory`보다 **먼저** 올라간다. 저장이 실패한 뒤 화면을 떠나면
어떤 행에도 안 걸린 파일이 버킷에 남았다. **실제로 사흘째 남아 있던 파일이 하나 있었다**
(`voice/70e586d7-…/86aceef3-….webm`, 2026-08-07) — 지웠다(§6-2).

정리 시점을 셋으로 나눴다:

| 언제 | 왜 |
|---|---|
| ×로 사진을 뺄 때 | 앞선 시도에서 이미 올라갔다면 그 파일은 다시 쓸 일이 없다 |
| "다시 녹음하기" | 같은 이유. 예전엔 ref만 비워서 파일이 남았다 |
| 화면을 떠날 때(언마운트) | 저장까지 못 간 것 전부. `committedRef`로 성공한 건 건드리지 않는다 |

**실패한 채 남아 있는 동안에는 지우지 않는다.** [다시 표현하기]가 그 파일을 그대로
다시 쓰기 때문이다 — "업로드가 실패해도 다시 고르게 하지 않는다"는 약속이 우선이다.
지우기가 실패해도 사용자를 막지 않되 **경로를 반드시 로그에 남긴다.** 못 지웠어도

## 6-4. 사진 타일 줄 수정 (2026-08-10, 캡처 `참고/마음표현하기_1·2.png`)

사용자가 실제 화면에서 두 가지를 짚었다. 둘 다 `compose-form.tsx` 사진 타일 줄만 손봤다.

### ① 카메라 타일의 위쪽 테두리가 잘려 보였다

**원인.** 타일 줄 `<ul>`이 `overflow-x-auto`다. CSS는 **가로만 잘라내게 둘 수 없다** —
한쪽이 `auto`면 다른 쪽 `visible`은 `auto`로 승격된다. 그래서 세로도 함께 잘린다.
카메라 `<li>`에는 위 여백이 없어서 분홍 2px 테두리와 포커스 링(3px + 2px 띄움)이
줄의 위 경계에 정확히 걸렸다.

**고친 것.** 카메라 `<li>`에 `pt-2`(8px), `<ul>`의 아래 여백을 `pb-1 → pb-2`.
바깥 wrapper의 `pt-2`는 이 문제와 무관하다 — 잘라내는 상자는 `<ul>` 자신이라
여백도 `<ul>` 안쪽에 있어야 한다.

### ② 카메라 타일과 사진 타일의 윗변이 어긋나 있었다

사진 `<li>`는 × 버튼 자리로 `pt-2 pr-2`를 갖고 카메라 `<li>`는 아무것도 없어서,
두 종류 타일이 **8px 어긋난 높이**에 걸려 있었다. ①의 `pt-2`가 이것도 같이 해결한다 —
두 종류가 같은 오프셋을 갖게 되어 윗변이 한 줄로 선다. 주석으로 "같은 값이어야 한다"고
못박아 두었다(하나만 바꾸면 다시 어긋난다).

### ③ 끌어서 사진 순서 바꾸기 (신규)

**대표 사진은 배열 0번**이라는 규칙은 이미 있었다(`index === 0`). 그래서 끌기 로직은
**배열 순서만 바꾼다.** 배지·업로드 순서·`memory_photos`의 자리는 전부 배열을 따라오므로
건드릴 곳이 한 군데뿐이다.

| 판단 | 고른 것 | 이유 |
|---|---|---|
| 구현 방식 | **포인터 이벤트 직접 구현**(`usePhotoReorder`) | HTML5 Drag and Drop은 모바일 브라우저에서 `dragstart`가 아예 안 일어난다. 그걸로 만들면 **마우스 쓰는 사람만** 쓰는 기능이 된다. 이 서비스는 손가락으로 쓰는 화면이다 |
| 라이브러리 | **안 씀** | 끌 대상이 한 줄 최대 10칸이고 필요한 동작이 "배열 순서 바꾸기" 하나뿐이다 |
| 시작 조건 | 손가락은 **꾹 누르기 260ms**, 마우스는 움직이는 즉시 | 이 줄은 옆으로 미는 줄이기도 하다. 손가락을 누르자마자 끌기로 잡으면 줄을 못 민다. 10px 넘게 움직이면 "미는 것"으로 보고 끌기를 포기한다 |
| 화면 따라 움직임 막기 | `touchmove`를 `passive:false`로 잡아 `preventDefault` | `pointermove`를 막아서는 스크롤이 안 멈춘다. 꾹 누르는 동안은 아직 스크롤이 시작되지 않아 이 시점에 막으면 걸린다 |
| 놓을 자리 표시 | **끄는 동안 배열을 바로바로 바꾼다** | 유령 칸을 따로 그리지 않아도 되고, **대표 사진 배지가 손가락을 따라 움직여** 결과가 미리 보인다 |
| 줄 끝 자동 밀기 | 넣음(양 끝 52px 안, 프레임당 12px) | 사진 10장이면 줄이 화면보다 훨씬 길다. 없으면 가려진 자리로는 옮길 방법이 없다 |

**새 사진이 붙는 자리는 지금처럼 배열 끝(오른쪽)으로 두었다.** 사용자의 "왼쪽일수록 최근"
이라는 말을 *"왼쪽일수록 표시 순서가 앞이다(= 대표에 가깝다)"* 로 읽었다. 끌기가 생긴
이상 순서는 사용자가 직접 정하는 것이고, 새로 담을 때마다 기존 배치를 밀어내며 자동으로
앞에 꽂히면 **애써 맞춰둔 순서가 담을 때마다 흐트러진다.**
→ **만약 "새로 담은 사진이 왼쪽에 와야 한다"는 뜻이었다면** `handlePick`의
`[...current, ...added]` 를 `[...added, ...current]` 로 바꾸면 된다(한 줄).

**꾹 누르라는 안내를 화면에 적었다.** 사진이 2장 이상일 때만
"사진을 꾹 눌러 끌면 순서를 바꿀 수 있어요. 맨 왼쪽이 대표 사진이에요."가 뜬다.
꾹 누르는 동작은 눌러보기 전에는 있는 줄도 모른다 — 안 적으면 아무도 못 쓰는 기능이 된다.

**키보드로 순서 바꾸기는 넣지 않았다.** 대신 × 로 빼고 원하는 순서로 다시 담는 길이
이미 있고, 이 화면의 사진은 방금 자기가 고른 10장 이하다. 화살표 키 재정렬은 "지금
몇 번째로 옮겨졌다"를 읽어주는 안내까지 함께 만들어야 제구실을 하는데, 그건 이 수정의
범위를 넘는다. **필요해지면 여기에 적어둔 것을 근거로 다시 판단할 것.**

### 마이그레이션 3건

| 이름 | 내용 |
|---|---|
| `memories_pin_and_soft_delete` | `memories.pinned_at`·`deleted_at` 추가, 부분 유니크 인덱스 `memories_one_pin_per_room_idx`(방당 고정 1개), 피드 정렬 인덱스 `memories_room_pinned_created_idx`, 함수 `pin_memory(uuid, boolean)` |

**컬럼을 지우지 않았다. 테이블도 새로 만들기만 했다.** 물리 삭제 금지 원칙 그대로다.

RLS는 `memory_photos`와 같은 방식 — 부모 게시물의 조건(`is_room_member` + `not has_blocked`)을
**그대로 다시 적었다.** 부모에 기대어 생략하면 나중에 `memories` 정책이 바뀔 때 여기만 조용히 샌다.

**`memory_hides`·`memory_saves`는 select까지 `user_id = auth.uid()`로 막았다.**
좋아요는 수를 세야 하니 방 멤버에게 열지만, 숨김·저장은 **남이 알 이유가 없는 표시**다.
누가 무엇을 숨겼는지 서로 보이면 같은 방을 쓰는 사이가 불편해진다.

### 왜 고정만 DB 함수(`pin_memory`)인가

`memories`의 UPDATE 정책은 **작성자 전용**이다. 여기에 "멤버면 UPDATE 허용"을 하나 더 붙이면
PERMISSIVE 정책끼리 OR로 합쳐져 **아무 멤버나 남의 글 문구까지 고칠 수 있게 된다**
(커밋 `c79f27b`이 겪은 함정, §1의 스토리지 정책과 같은 이유).
그래서 정책 대신 `security definer` 함수 하나만 열었다 — 이 문으로는 `pinned_at` 말고는 못 바꾼다.
"방당 고정 1개"도 앱이 아니라 이 함수 + 부분 유니크 인덱스가 지킨다.

### 판단들

**① 고정은 방 멤버 누구나 할 수 있다** (작성자 전용으로 묶지 않았다).
앨범방은 함께 쓰는 공간이고 고정은 "이 글이 지금 우리에게 중요하다"는 **공용 큐레이션**이다.
오늘 맨 위에 둘 사진을 정하는 사람이 그 사진을 찍은 사람이라는 법은 없다.
되돌리기도 한 번에 되고, 방 안은 이미 서로를 믿는 사이라는 전제 위에 서 있다.
**수정·삭제는 반대다** — 그건 남의 기록을 바꾸는 일이라 `author_id === 지금 로그인한 사람`일 때만
메뉴에 그린다(회색으로 눌리지 않게 두지 않는다. "왜 안 되지" 하고 계속 누르게 된다).

**② 한 방에 고정은 하나. 새로 고정하면 이전 고정이 자동으로 풀린다.**
"맨 위 한 자리"가 여럿이면 고정한 의미가 없어진다. 물어보지 않고 정한 이유:
고정이 여러 개인 화면은 캡처에도 없고, 실수해도 다시 눌러 되돌릴 수 있다.

**③ 수정은 문구(description)만이다.** 사진·음성을 다시 고르게 하는 것은 "고치기"가 아니라
처음부터 다시 담는 일이라 작성 화면의 몫이다. 오탈자를 고치는 정도만 연다.

**④ 저장(북마크)은 토글과 DB만 만들었다. 저장한 목록을 보는 화면은 없다.**
지금은 메뉴가 "저장 취소"로 바뀌는 것으로만 확인된다. 범위를 넘기지 않으려고 멈춘 자리이니,
"저장한 추억" 화면을 만들 때 이 표를 근거로 이어갈 것.

**⑤ 숨기기는 되돌릴 길이 없다.** 감춘 글은 피드에서 사라지므로 ⋯ 메뉴를 다시 열 수가 없다.
`memory_hides` 행을 지우는 액션은 만들지 않았다 — 부를 화면이 없는 액션이기 때문이다.
"숨긴 글 보기" 화면이 생기면 그때 해제를 붙인다.

**⑥ 삭제는 소프트 삭제인데, 사용자에게는 "되돌릴 수 없어요"라고 말한다.**
DB에는 `deleted_at`만 채워져 행이 남지만, **화면에서 영영 사라지고 사용자가 되돌릴 길이 없는 것은
사실**이다. "사실은 안 지워져요"라고 안심시키면 그게 거짓말이 된다.
지울 때 `pinned_at`도 함께 비운다 — 지워진 글이 "이 방의 고정"으로 남아 있으면
되살릴 때 아무도 시키지 않은 자리에 가 있게 된다.

**⑦ 좋아요는 낙관적 업데이트를 쓰지 않았다.** 누르면 서버 액션 → `revalidatePath` →
서버가 다시 센 수가 내려온다. 클라이언트가 수를 직접 +1 하면 같은 순간 옆 사람이 누른
좋아요가 사라진 것처럼 보인다(FavoriteButton과 같은 판단).

### 조회 (N+1 없음)

- 피드는 `deleted_at is null` + `order(pinned_at desc **nulls last**, created_at desc)`로 읽는다.
  `nullsFirst: false`를 빼먹으면 내림차순의 기본값이 NULLS FIRST라 **고정 안 한 글이 위로 온다.**
- 숨긴 글은 **목록에 들어오기 전에** 뺀다(`not.in`). 30개를 받아온 뒤 빼면 숨긴 만큼 화면이 짧아진다.
  `memory_hides`에 방 번호가 없어서 부모 게시물(`memories!inner`)로 이 방 것만 좁혔다.
- 좋아요·저장은 게시물 번호를 모아 **각각 한 번씩** 읽는다(홈 화면의 배치 조회와 같은 방식).
  좋아요는 `user_id`까지 받아온다 — 수만 세면 **내 하트가 채워졌는지**를 알 수 없다.

## 6-6. 더보기 서랍 — 갤러리·좋아요·별명·숨김·나가기 (2026-08-10, 신규 기능)

> 기준: `참고/앨범방_더보기.png`. §3-①과 §7이 "5단계"로 미뤄뒀던 햄버거 드로어가 여기서 들어왔다.

### 마이그레이션 1건

| 이름 | 내용 |
|---|---|
| `room_members_nickname` | `room_members.nickname text null` 추가 + CHECK `room_members_nickname_length` |

**RLS는 새로 만들지 않았다.** `room_members_update`가 이미
`user_id = auth.uid() or is_room_admin(room_id)`라 본인 행을 고칠 수 있다.
앱은 항상 `.eq('user_id', 나)`를 함께 걸어 남의 별명을 건드리지 않는다(실제로 0줄임을 확인, 아래 표).

### 별명을 `relationship_label`에 얹지 않고 컬럼을 새로 만든 이유

| | `relationship_label` (기존) | `nickname` (신규) |
|---|---|---|
| 누가 정하나 | **초대한 사람** | **본인** |
| 뜻 | "내가 이 사람을 이렇게 부른다" | "내가 이 방에서 이렇게 불린다" |
| 언제 | 초대장을 만들 때 한 번 | 아무 때나, 몇 번이든 |
| 비어 있을 수 있나 | 아니오 (NOT NULL) | 예 (null = 전역 이름을 쓴다) |

컬럼 하나를 아끼려고 겹쳐 쓰면 **별명을 저장하는 순간 초대한 분이 적어둔 호칭이 덮여 사라진다.**
물리 삭제 금지 원칙에 걸리는 데다, 방 설정 화면이 지금 그 값을 "이 방에서 부르는 호칭"으로
쓰고 있어 뜻이 뒤엉킨다. 무엇보다 NOT NULL이라 **"아직 안 정했다"를 표현할 수가 없어서**
"별명이 없으면 전역 이름" 규칙 자체가 성립하지 않는다. 그래서 새 컬럼이다.

CHECK는 `btrim(nickname) = nickname and char_length between 1 and 20` —
앞뒤 공백이 붙은 이름과 빈 문자열을 DB가 직접 막는다. 저장하는 쪽은 trim 후 비면 null을 넣는다
("안 정했다"와 "빈 이름"은 다른 것이라 빈 문자열로 남기지 않는다).

### 이름을 고르는 규칙을 한 곳에 모았다 — `src/lib/member-name.ts`

`roomMemberName({ userId, nickname, name })` 하나가 정한다:
탈퇴(userId null) → "탈퇴한 사용자", 별명 있으면 별명, 없으면 전역 이름, 그것도 없으면 "알 수 없는 사람".

쓰는 곳: 피드·갤러리·좋아요·숨김(= `buildMemoryCards`), 방 설정 구성원 목록·방장 승계 안내,
홈 카드의 멤버 아바타. **같은 사람이 화면마다 다른 이름으로 보이면 두 화면이 서로 다른 사람
얘기를 하는 것처럼 읽힌다.**

별명 조회는 `status`로 좁히지 않는다 — 방을 떠난 분이 남긴 글도 **그 방에서 불리던 이름**으로 남아야 한다.

### 조회를 한 곳으로 모았다 — `src/lib/room-feed.ts`

피드·좋아요·숨김 세 화면이 같은 카드를 그린다. 같은 서명·좋아요·저장·이름 정하기를
세 벌 적어두면 한 곳만 고쳐져 조용히 어긋난다(§6-5의 "숨긴 글 빼기"가 정확히 그런 규칙이다).

- `MEMORY_CARD_SELECT` — `as const`라 supabase-js 타입 추론이 살아 있다(문자열을 이어 붙이면 unknown이 된다)
- `buildMemoryCards({ rows })` — 사진 정렬 → 서명(버킷당 1회) → 좋아요·저장 배치 조회 → 이름. **N+1 없음**
- `loadHiddenMemoryIds` / `loadRoomNicknames` / `signPaths` / `isRoomPath`

`revalidateRoom`을 `revalidatePath(경로, 'layout')`으로 넓혔다. 방 아래에 같은 게시물을 보여주는
화면이 여럿이 됐기 때문이다 — 좋아요 목록에서 ♡를 껐는데 그 목록이 그대로 남아 있으면
"눌렀는데 아무 일도 안 일어난" 것처럼 보인다.

### 판단들

**① 서랍은 `<dialog>` + `showModal()`이다.** 초점 가두기·Esc로 닫기·뒤 화면 잠금이
브라우저에 이미 들어 있다(MemoryMenu의 확인 창, cover-crop-dialog와 같은 판단).
창 자체가 화면 전체이고 그 안에서 흰 판이 오른쪽에 붙는다 — 그래야 **어두운 쪽을 누르면 닫힌다**
(`event.target === dialog`). 미는 동작은 `translate-x-full → 0` 한 번이고 `motion-reduce`에서는 없다.

**①-1 창에 `fixed inset-0`을 직접 적었다 (안 적으면 화면 밖에서 열린다).**
브라우저 기본값(`dialog:modal`)은 창을 **세로로만** 붙여두고 가로는 *놓인 자리*(static position)를 쓴다.
이 부품은 머리띠 **오른쪽 끝**에 있어서 그대로 두면 100vw짜리 창이 그 자리에서 시작해
판이 화면 밖으로 밀려난다. `m-auto`로 가운데 정렬하는 작은 확인 창(MemoryMenu)에는 없던 문제다.

**② 갤러리 미리보기를 위해 조회를 더 하지 않는다.** 피드가 이미 서명해 둔 주소에서
가장 최근 게시물 3개의 대표 사진을 골라 쓴다(카드 순서는 고정 글이 맨 위라 여기서 시간순으로 다시 센다).
서랍은 늘 그려지는 부품이라, 여기에 조회를 하나 붙이면 **피드를 열 때마다** 값을 치른다.

**③ 미리보기 사진은 누르는 자리가 아니다.** 바로 위 "갤러리"가 이미 전체 사진으로 가는 문이다.
같은 곳으로 가는 문을 둘 두면 낭독기에도 같은 링크가 두 번 읽힌다.

**④ 갤러리·좋아요 목록에서 내가 숨긴 글을 뺐다.** 지시문은 `deleted_at`만 말했지만,
피드에서 안 보이기로 한 것이 갤러리에 그대로 있으면 숨김이 반쪽이 된다.
숨긴 것을 다시 보는 자리는 `/hidden` 하나로 모았다. **되돌리려면** 각 화면의
`not in (hidden)` 조건을 빼면 된다(한 줄씩).

**⑤ 갤러리 정렬에서 고정(`pinned_at`)은 보지 않는다.** 고정은 피드에서 "맨 위 한 자리"를
정하는 표시다. 갤러리까지 순서를 흔들면 "언제 찍은 사진인지"로 훑는 흐름이 끊긴다.
왼쪽 위 = 가장 최근 게시물의 대표 사진, 그 다음이 같은 게시물의 sort_order 순이다.

**⑥ 갤러리는 게시물 120개·사진 240장에서 끊는다.** 서명을 한 번에 몰아서 하므로
수가 커지면 첫 그림이 그만큼 늦어진다. 끊길 때는 화면에 적는다 — 조용히 자르면 사진이 사라진 줄 안다.
(더 보려면 페이지 나누기가 필요하다. 이번 범위 밖이다)

**⑦ 홈의 "게시물 N개"가 지운 글까지 세고 있었다.** §6-5에서 소프트 삭제가 들어왔는데
`src/app/page.tsx`의 집계에는 `deleted_at is null`이 없었다. 방 안에서 보이는 수와 홈의 수가
어긋나는 자리라 한 줄 고쳤다. **이번 작업 범위 밖이지만 같은 원칙(지운 글은 없는 것)의 구멍이다.**

**⑧ 나가기는 새로 만들지 않고 `/settings#leave`로 보낸다.** 나가면 무슨 일이 생기는지
설명하는 글이 이미 `leave-panel.tsx`에 있다. 두 벌로 나뉘면 한쪽만 고쳐진다.
덤으로 방 설정(구성원 목록·차단)으로 가는 길이 서랍을 통해 유지된다 —
머리띠에서 [방 설정] 버튼이 빠진 자리를 이것이 메운다.

**⑨ 별명은 개인 설정이 아니라 그 방의 내 멤버십이다.** 그래서 **다른 멤버에게도 이 이름으로 보인다.**
"내가 이 방에서 불리는 이름"이지 "내가 남을 부르는 이름"이 아니다.
저장하면 피드로 돌려보낸다 — 바뀐 이름이 실제로 어떻게 보이는지 그 자리에서 확인된다.

### 확인한 것 (DB, 실제 로그인 사용자 역할로)

`set local role authenticated` + `request.jwt.claims`로 **RLS가 실제로 도는 상태**에서
확인하고 전부 `rollback` 했다(DB에 남긴 것 없음).

| 확인한 것 | 결과 |
|---|---|
| 별명 저장 후 작성자 이름 | 게시물 이름이 `김민지` → **`민지엄마`** (전역 이름을 안 건드리고 이 방에서만) |
| 갤러리 정렬 | 새 게시물 사진(sort 0,1) → 옛 게시물 사진(sort 0,1,2). **왼쪽 위 = 가장 최근 게시물의 대표 사진** |

### ⚠️ 브라우저 실확인 — **못 했다**

§6-5·§6-4와 같은 이유다. 같은 시간에 도는 다른 이식 작업이 chrome-devtools의 공용 프로필
(`~/.cache/chrome-devtools-mcp/chrome-profile`)을 잡고 있어 접속이 계속 거절됐다
(`The browser is already running for …`). 로그인 세션이 그 프로필 안에만 있어 우회할 수 없다.

**아래는 눈으로 봐야 끝난 것이다. 다음에 브라우저를 잡는 사람이 이 표를 그대로 밟을 것:**

| 확인할 것 | 보아야 할 것 |
|---|---|
| 머리띠 ≡ 누르기 | 오른쪽에서 판이 밀려 들어오고 왼쪽이 어두워진다. "더보기" 제목 + X |
| 어두운 쪽·Esc | 둘 다 닫히고 초점이 ≡ 버튼으로 돌아온다 |
| 갤러리 미리보기 | 최근 게시물 3개의 대표 사진이 64px 썸네일로. 사진이 없으면 "사진이 아직 없어요" |
| 갤러리 화면 | 3열 격자, **왼쪽 위가 가장 최근 게시물의 대표 사진** |
| 좋아요 화면 | ♡ 누른 글만. 여기서 ♡를 다시 누르면 목록에서 빠진다 |
| 별명 설정 | 저장 → 피드로 돌아오고 **내 카드 이름이 별명으로** 바뀐다. 마이 탭 이름은 그대로 |
| 별명 비우고 저장 | 원래 이름으로 돌아온다 |
| 숨김 화면 | 숨긴 글이 보이고 [다시 보이게 하기]를 누르면 목록에서 빠져 피드로 돌아온다 |
| 앨범방 나가기 | 방 설정 화면의 나가기 칸으로 **스크롤된 채** 열린다(#leave) |
| 44px·17px | 서랍 각 줄의 실제 높이와 글자 크기 |
